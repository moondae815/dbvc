# SSMS 수동 확인

CI가 검증하지 못하는 영역(WPF 렌더링, VS 패키지 로딩, `.vsct` 메뉴, 옵션 페이지 등록, SSMS 통합,
실제 DB 연결, 실제 AI 프로바이더 호출)을 SSMS 21에서 직접 눌러 보는 항목을 모았다.
2026-09-19 기준(0.9.5).

**여기 없는 것은 어디에.** 설치 절차는 [`setup-checklist.md`](setup-checklist.md), 팀이 지켜야 할
규칙과 조직이 정해야 할 것은 [`rollout-announcement.md`](rollout-announcement.md), 남은 일과
우선순위는 [`team-rollout-backlog.md`](team-rollout-backlog.md)에 있다.

**항목은 1부에서 2부로만 흐른다.** 1부는 아직 한 번도 확인하지 않은 것, 2부는 확인해 본 적이
있어 릴리스마다 다시 보는 것이다. 1부에서 밟았으면 날짜를 적고 **2부의 해당 묶음으로 옮긴다** —
양쪽에 두지 않는다. 같은 항목이 두 군데에 있으면 어느 쪽이 사실인지 알 수 없게 되고, 그것이
이 문서와 `setup-checklist.md` 사이에서 실제로 일어났던 일이다.

**1부에만 체크박스가 있다.** 2부는 "확인했는가"가 아니라 "언제 마지막으로 봤는가"를 들고 있으므로
체크박스 대신 **마지막 확인** 날짜를 붙인다. 릴리스마다 훑고 그 날짜를 갱신한다.

## 적는 법

- **1부:** 확인했으면 `[x]`로 바꾸고 줄 끝에 `— YYYY-MM-DD` 를 붙인 뒤, 묶음 머리가 가리키는
  2부 자리로 옮긴다.
- 실패했으면 체크하지 말고 바로 아래에 `> 실패: 증상` 을 적는다.
- 해 보지 않고 넘길 항목은 `> 보류: 사유` 를 적는다.
- **2부:** 훑은 뒤 `— 마지막 확인: YYYY-MM-DD` 를 갱신한다. 실패하면 그 항목을 **1부로 되돌린다.**

# 1부. 지금 남은 것

**기록이 없다는 것이지 안 했다는 뜻은 아니다.** 계획서의 체크박스는 근거로 쓰지 않았다 — 실기로
확인한 AI 기능 계획서도 전부 비어 있을 만큼 채우는 습관이 들쭉날쭉하다. 대신
`team-rollout-backlog.md`, 커밋 메시지, `superpowers/HANDOFF-2026-08-31.md`에 남은 실기 기록과
대조했다.

기능(버전)별이 아니라 **한 번 앉아서 이어 밟을 수 있는 준비 상태**별로 묶었다. 같은 클론·같은
화면에서 끝나는 것끼리 모여 있다.

> **묶음 기호(B-3, C-1, …)는 그대로 둔다.** 커밋 메시지와 백로그가 이 기호로 항목을 가리키고
> 있어, 다시 매기면 그 참조가 끊긴다. 2부로 내려간 묶음(A·E·G, D-1, B-1, B-2)의 자리가 비어
> 보이는 것은 그 때문이다.

## B-3. 변경 로그 정리 실패 안내 (0.5.14)

> 밟으면 날짜를 적고 **2-4. 변경 로그와 추적기**로 옮긴다.

**이 경로는 CI가 닿지 못한다.** 단위 테스트가 사유 문구와 GRANT 내용까지는 보지만, 상자가 실제로
뜨는지와 배너가 사라지는지는 SSMS에서 눌러야 안다.

배너와 **추적기 업데이트**는 2026-09-09 v5 → v6 업그레이드에서 밟았다(2-4에 있다). 남은 것은
권한과 실패 경로다. 준비: **`sysadmin`이 아닌 계정.**

- [ ] **권한이 실제로 부여됐는지.** `setup-checklist.md` 5단계 "일상 사용에 필요한 권한"의 조회
      쿼리를 실행 → `SELECT`·`UPDATE` 두 줄이 나온다
- [ ] **실패 안내.** 일부러 깨뜨려 확인한다. SSMS 쿼리 창에서:
  ```sql
  DENY UPDATE ON [dbo].[DBVC_ChangeLog] TO [public];
  ```
  `db_owner`가 **아닌** 계정으로 접속해(공용 SQL 계정이면 그 계정으로) 객체 하나를 고치고
  **새로고침 → 체크 → Commit** 한다.

  > **`sysadmin`으로 접속하면 이 확인이 성립하지 않는다.** `sysadmin`은 권한 검사를 통째로
  > 건너뛰므로 `DENY`가 걸려도 커밋이 정상으로 끝나고, 상자가 뜨지 않는 것을 결함으로 오인하게
  > 된다. 확인용 계정이 `sysadmin`인지 먼저 본다: `SELECT IS_SRVROLEMEMBER('sysadmin');` → `0`.
  - [ ] 상자가 뜨고 제목이 **"DBVC 커밋 — 변경 로그 정리"** 다 (제목에 "실패"가 없어야 한다 —
        커밋 자체는 성공했으므로)
  - [ ] 본문이 **커밋은 성공했다 / 항목이 다시 나타난다 / `db_owner`가 [변경 추적기 업데이트]를
        누르면 된다** 세 가지를 모두 말한다
  - [ ] 상자를 닫으면 새로고침이 돌고, **그 항목이 목록에 그대로 남아 있다** (안내가 사실인지)
- [ ] **원상 복구.** `REVOKE`가 `DENY` 항목을 걷어낼 뿐 `GRANT`를 되살리지는 않으므로 두 문장을
      모두 실행한다. 그 뒤 다시 커밋하면 항목이 목록에서 사라진다
  ```sql
  REVOKE UPDATE ON [dbo].[DBVC_ChangeLog] FROM [public];
  GRANT  UPDATE ON [dbo].[DBVC_ChangeLog] TO   [public];
  ```
- [ ] **정상 경로에 상자가 뜨지 않는지.** 위를 되돌린 뒤 평범한 커밋을 한 번 더 한다 →
      **아무 상자도 뜨지 않는다.** 여기서 뜨면 커밋마다 클릭이 하나 늘어난 것이므로 결함이다

## C-1. 이력 탭 분할선과 병합 안내 (0.5.12 · 0.5.13)

> 밟으면 날짜를 적고 **2-7. 이력과 비교 창**으로 옮긴다.

**WPF 레이아웃이라 CI도 단위 테스트도 최종 근거가 못 되는 자리다.** 헤들리스 테스트가
행 높이와 Visibility까지는 보지만, 분할선이 실제로 **끌리는지**는 눌러 봐야 안다.

준비물은 커밋이 여러 개 쌓인 개발 클론뿐이다.

### A. 분할선 — 전체 이력 모드

머리글 왼쪽이 `저장소 전체`인 상태다. 목록에서 객체를 고르지 않았거나 **전체 이력으로**를
누르면 이 상태가 된다.

- [ ] 커밋을 고르기 **전**: 이력 목록이 탭을 꽉 채우고 **분할선이 하나도 없는지**
      (0.5.13에서 고쳤다. 전에는 머리글만 있는 빈 변경 파일 목록이 탭의 절반을 차지했다.
      필터 모드와 같은 규칙이다 — 담길 것이 없으면 접는다)
- [ ] 커밋을 하나 고른다 → 가운데에 **변경된 파일 목록**이 뜨는지
- [ ] 그 목록에서 파일을 하나 고른다 → 아래에 좌우 Diff가 뜨는지
- [ ] 이제 분할선이 **두 개**인지 — 이력 목록 바로 밑(바깥)과 변경 파일 목록 바로 밑(안쪽).
      커서를 올리면 위아래 화살표로 바뀌는 자리가 분할선이다. 안 바뀌면 거기엔 없는 것이다
- [ ] **안쪽** 분할선을 끈다 → 변경 파일 목록과 Diff만 늘고 주는지.
      **이력 목록 높이는 그대로**여야 한다 (이 동작은 0.5.12에서 바뀌지 않았다)
- [ ] **바깥** 분할선을 끈다 → 이력 목록이 늘고 주는 만큼, 아래 두 패널이 서로의 비율을
      유지한 채 **함께** 움직이는지
      (**0.5.12에서 바뀐 동작이다.** 전에는 변경 파일 목록만 움직이고 Diff는 가만히 있었다)
- [ ] 분할선을 끌어 둔 채 **다른 커밋을 고른다** → 방금 끌어 둔 비율이 그대로 남는지
      (클릭 한 번에 반반으로 튀면 회귀다 — 커밋 03dcdf8이 고쳤던 자리다)
- [ ] 위에서 다른 커밋을 고른 직후를 그대로 본다 — 커밋을 바꾸면 파일 선택이 풀려 Diff가
      접힌다. 이때 변경 파일 목록이 그 자리를 채우고 **안쪽 분할선이 사라지는지**
      (그 자리에 5px짜리 회색 빈 띠가 남으면 결함이다. **0.5.12에서 함께 고친 자리다**)

### B. 분할선 — 필터 모드 (0.5.12에서 고친 것)

개체 탐색기에서 객체를 우클릭 → **DBVC: 이력 보기**, 또는 변경 목록에서 객체를 고르면
이 상태가 된다. 머리글 왼쪽이 `스키마.객체명`으로 바뀐다.

- [ ] 커밋을 고르기 **전**: 이력 목록이 창을 꽉 채우고 **분할선이 하나도 없는지**
      (변경 파일 목록도 Diff도 없어 나눌 경계가 없다. 목록 밑에 회색 빈 띠가 남으면 결함이다)
- [ ] 커밋을 하나 고른다 → 아래에 Diff가 **바로** 뜨는지.
      이 모드에서 **변경 파일 목록이 뜨지 않는 것은 정상이다** — 볼 파일이 이미 하나로 정해져 있다
- [ ] 이제 분할선이 **정확히 하나**, 이력 목록과 Diff 사이에 있는지
- [ ] **그 분할선을 끌어 이력 목록과 Diff의 비율이 바뀌는지 — 이것이 0.5.12에서 고친 것이다.**
      전에는 두 패널이 반반으로 굳어 조절할 방법이 없었다
- [ ] **전체 이력으로**를 누른다 → 머리글이 `저장소 전체`로 바뀌는지. 이때는 고른 커밋이
      없으므로 A의 첫 항목과 같은 상태, 즉 **분할선이 하나도 없는 것**이 정상이다
- [ ] 이어서 커밋과 파일을 다시 고른다 → 분할선이 두 개가 되고, **A에서 끌어 두었던
      비율이 그대로 살아 있는지** (반반으로 초기화되면 회귀다)

### C. 병합 안내 — 위치

**병합 커밋이 없으면 만들어야 한다.** 아직 push하지 않은 저장소에서만 아래 절차를 쓴다.

```powershell
cd <저장소 폴더>
git switch -c tmp-merge-check
# 아무 .sql 파일 하나를 열어 주석 한 줄을 더하고 저장한다
git commit -am "임시: 병합 확인용"
git switch main
git merge --no-ff tmp-merge-check -m "임시: 병합 확인용 머지"
```

확인이 끝나면 되돌린다 — **push한 뒤라면 `reset --hard`를 쓰지 말고 그냥 남겨 둔다.**

```powershell
git reset --hard HEAD~2
git branch -D tmp-merge-check
```

- [ ] DBVC에서 **새로고침** → 이력 탭 목록에 방금 만든 병합 커밋이 뜨는지
- [ ] 그 행의 **종류** 열에 `병합`이 적혀 있는지
- [ ] 그 행을 고르면 **머리글 줄**(왼쪽 `저장소 전체` 표시 오른쪽)에 황갈색으로
      `병합 커밋입니다 — 첫 부모 기준으로 비교합니다.` 가 뜨는지.
      **0.5.12에서 옮긴 자리다** — 변경 파일 목록 패널 안이 아니라 머리글이어야 한다
- [ ] 병합이 아닌 커밋으로 옮기면 그 문구가 사라지는지
- [ ] 도구 창을 **좁게 도킹**한다 → 문구가 줄바꿈되지 않고 `…`로 잘리며 머리글이 한 줄을
      유지하는지, 그 위에 마우스를 올리면 ToolTip으로 전문이 보이는지
      (머리글이 두세 줄로 늘어나면 결함이다)

### D. 병합 안내 — 필터 모드

C에서 고친 그 `.sql` 객체를 개체 탐색기에서 우클릭 → **DBVC: 이력 보기**로 연다.

- [ ] 병합 커밋이 목록에 **보이면**, 머리글 안내도 함께 뜨는지
      (**0.5.12 전에는 이 모드에서 안내가 아예 보이지 않았다** — 안내가 접히는 패널 안에 있었다)

> **목록에 병합 커밋이 안 보여도 결함이 아니다.** 좁힌 이력은 `git log -- <경로>` 와 같은
> 경로 단순화를 해서, 병합 결과가 어느 한쪽 부모와 같으면 그 병합을 목록에서 지운다.
> 위 절차로 만든 단순 병합이 정확히 그 경우다. 굳이 보이게 하려면 양쪽 브랜치에서 **같은
> 파일의 같은 줄**을 다르게 고쳐 충돌을 낸 뒤 손으로 풀어 병합해야 한다 — 그때 남는 병합이
> 바로 "첫 부모 기준"이라는 사실이 실제로 필요한 커밋이다.

### E. 잘림 안내 (조건이 맞을 때만)

한 커밋에 파일이 500개를 넘으면 같은 머리글 자리에 `전체 N개 중 500개만 표시합니다.` 가
뜬다. 객체가 500개를 넘는 DB에서 **전체 다시 추출** 한 뒤의 첫 커밋이 그렇다. 그런 DB가
없으면 보류한다.

- [ ] 그런 커밋이 있으면 골라서, 안내의 `N`이 실제 커밋에 담긴 파일 수와 맞는지.
      DBVC와 같은 첫 부모 기준으로 `(git diff --name-only <SHA>^ <SHA>).Count` 를 세어
      대조한다 — 병합 커밋에서도 이 형태를 써야 한다
      (`git show --name-only` 는 병합에서 아무것도 내지 않는다)
- [ ] 병합이면서 잘리기도 한 커밋에서는 두 문구가 한 줄에 이어 붙는지
      (`병합 커밋입니다 … 전체 N개 중 500개만 표시합니다.`)

## F. 배포·감사 클론 — 병합 (0.8.0)

### F-0. 준비 — 지금 환경으로는 절반만 된다

**환경 브랜치 이름이 코드에 박혀 있다** — `develop`과 **`master`** 다(`EnvironmentBranches`). 검증용
원격(`db-schema-Northwind`)의 운영 브랜치는 `main`이라, 그대로 두면 운영 클론 쪽 판정(경고 A, 테스트
반영 열)이 아예 켜지지 않고 `main`이 병합 후보 목록에 섞여 나온다.

> 2026-09-18에 `main` 고정 배포 클론으로 실제로 보았다 — **테스트 반영** 열은 그려지지만 칸이 늘
> 비고, 화면은 왜 비는지 말하지 않는다. 사유와 고칠 때의 선택지는 `team-rollout-backlog.md`
> 13번에 있다. 아래 준비를 갖추기 전에는 F절의 판정을 본 것으로 치지 않는다.
>
> 병합 → 차이 검사 **한 바퀴 자체**는 2026-09-19에 그 클론으로 돌려 봤다(2-10에 있다).
> 그러므로 이 절에 남은 것은 화면이 아니라 **`master`가 있어야 켜지는 판정과 원격 경합**이다.

- [ ] 원격에 `master` 브랜치를 만든다 (`main`에서 분기해 Push)
- [ ] **테스트 클론:** 배포 용도, 고정 브랜치 `develop`. 지금의 `Northwind_Deploy` 매핑이 `main`
      고정이므로 `develop`으로 다시 연결한다
- [ ] **운영 클론:** 고정 브랜치 `master`. 매핑이 DB 단위라 **DB가 하나 더 필요하다** — 예: `Northwind`를
      백업·복원한 `Northwind_Prod`. **감사 용도로 연결하면** 설계가 감사에도 병합을 연 것(`MappingPolicy`)까지
      함께 확인된다
- [ ] 티켓 브랜치를 개발 클론에서 준비해 Push한다
  - 서로 다른 객체를 고친 브랜치 둘 이상 (정상 병합, 테스트 반영 열)
  - 같은 `.sql`의 **같은 줄**을 다르게 고친 브랜치 둘 (충돌)
  - 같은 객체를 **다른 줄**에서 고친 브랜치 둘 (운영 클론의 "확인 필요")

### F-1. 테스트 클론 (`develop`)

- [ ] [병합할 브랜치 확인] → 목록에 `develop`·`master`가 없다
- [ ] 브랜치를 고르면 오른쪽에 바뀔 파일이 뜬다
- [ ] [병합] → 확인 → 원격에 병합 커밋이 보이고, DBVC 이력 탭 **종류**가 `병합`이다
- [ ] 병합 뒤 "차이 검사를 시작할까요?"에 확인 → Pull이 곧바로 끝나고 병합된 객체가 차이로 뜬다
- [ ] 같은 줄을 다르게 고친 브랜치 → 미리보기에 충돌이 뜨고 [병합]이 잠긴다
- [ ] 목록의 **테스트 반영** 열은 남아 있고 칸이 비어 있다

### F-2. 운영 클론 (`master`)

- [ ] **테스트 반영** 열이 `develop`에 병합된 브랜치에만 `반영됨`이다
- [ ] 같은 객체를 만진 브랜치 둘 중 하나를 고르면 미리보기에 **"확인 필요"** 가 뜨고, [병합]의 확인 대화상자에도 실린다

### F-3. 원격 경합과 실패

사람 둘이 필요한 상황은 개발 클론에서 원격에 직접 Push해 흉내 낸다.

- [ ] 미리보기 뒤 [병합] 전에 개발 클론에서 목적지 브랜치(`develop`)에 먼저 Push한다 → 오류·거부 안내가
      뜬 뒤 클론이 깨끗하다(`git status` 깨끗, 병합 전 커밋). [병합할 브랜치 확인]부터 다시 하면 병합된다
- [ ] 원격에서 브랜치 하나를 지운 뒤 [병합할 브랜치 확인] → 그 브랜치가 목록에서 사라진다
- [ ] 미리보기를 본 뒤 **그 원본 브랜치**에 새 커밋을 올리고 [병합] → "미리보기 뒤 … 새 커밋이
      올라왔습니다"로 거부되고, 원격의 목적지 브랜치가 그대로다

### F-4. 다른 화면과의 경계

- [ ] 개발 클론에서는 병합 영역이 보이지 않는다
- [ ] 병합 영역이 생긴 배포·감사 클론에서도 커밋·**Push** 버튼은 여전히 잠겨 있다 — 병합은 자기가 만든
      병합 커밋 하나만 올리고, Push 자체는 열지 않았다(`MappingPolicy`)

## 2-2. 추출과 변경 목록

### 추출 형식과 속도 (0.3.0)

- 새로 추출한 **프로시저·뷰·함수 `.sql` 이 `CREATE OR ALTER` 로 시작**한다 — 마지막 확인: 기록 없음
- **테이블 `.sql` 은 `CREATE TABLE` 그대로**다 (T-SQL에 `CREATE OR ALTER TABLE`이 없다) — 마지막 확인: 기록 없음
- **객체가 많은 실제 개발 DB**에서 프로시저 하나만 고치고 **새로고침** → 체감으로 몇 초 안에 끝난다 (객체 수에 비례해 느려지면 열거 비용이 되살아난 것이다) — 마지막 확인: 기록 없음
- **전체 다시 추출** 중에 쿼리 편집기와 개체 탐색기가 그대로 쓰인다 — 마지막 확인: 기록 없음
- SSMS **테이블 디자이너로 새 테이블을 만든** 뒤 **새로고침** → `수정`이 아니라 `추가`로 뜬다 (디자이너는 저장 한 번에 `CREATE_TABLE` 뒤로 `ALTER_TABLE`을 더 흘린다) — 마지막 확인: 기록 없음
- 기본값 제약과 인덱스를 가진 테이블을 만든 뒤 **새로고침** → 비교창의 스크립트에 `DEFAULT` 제약과 `CREATE ... INDEX` 가 함께 들어 있다 — 마지막 확인: 기록 없음

### 이름 변경과 테이블 디자이너 (0.3.1)

**0.3.0에서 저장소의 파일이 지워질 수 있던 자리다.**

- 테이블 하나를 커밋해 둔 뒤, **SSMS 테이블 디자이너로 열의 형식만 바꾸고**(예: `nvarchar(50)` → `nvarchar(200)`) 저장 → **새로고침** → 그 테이블이 **`수정`으로 뜬다** (`삭제`로 뜨면 커밋하는 순간 저장소에서 그 `.sql`이 지워진다) — 마지막 확인: 기록 없음
- 같은 상태에서 목록에 **`Tmp_`로 시작하는 항목이 없다** (SQL Server가 재작성에 쓰는 임시 이름이라 실제로 존재한 적이 없다. 선택해도 비교창이 비어 있다) — 마지막 확인: 기록 없음
- 그대로 **커밋** → 저장소의 그 테이블 `.sql` 에 **바뀐 열 형식이 들어가 있고 파일이 남아 있다** — 마지막 확인: 기록 없음
- 프로시저 하나를 커밋해 둔 뒤 `sp_rename` 으로 이름을 바꾸고 **새로고침** → **새 이름이 `수정`(또는 `추가`)으로** 뜨고 **옛 이름은 `삭제`로** 뜬다 — 마지막 확인: 기록 없음
- 그대로 커밋 → 저장소에 **새 이름의 `.sql` 이 생기고 옛 이름의 파일은 사라졌다** — 마지막 확인: 기록 없음
- **컬럼** 이름을 `sp_rename` 으로 바꿔도 → 부모 **테이블의 수정**으로 뜬다 (컬럼의 새 이름이 테이블 이름을 밀어내면 결함이다) — 마지막 확인: 기록 없음
- 디자이너로 **두 번** 저장하고 각각 커밋 → **두 번째 커밋 뒤 목록이 빈다** (같은 테이블이 계속 `수정`으로 다시 올라오면 옛 이름의 로그 행이 닫히지 않은 것이다. 한 번 그렇게 되면 `.sql`이 이미 같아져 다시 커밋해서 지울 수도 없다) — 마지막 확인: 기록 없음
- 객체를 `DROP` 한 뒤 **커밋하지 않은 채 새로고침을 두 번** → 두 번째에도 `삭제`가 **목록에 남아 있다** (사라지면 선택할 수 없어, 없어진 객체의 `.sql`이 저장소에 영영 남는다) — 마지막 확인: 기록 없음

## 2-3. 작업자 필터와 커밋 전 확인

공용 계정 환경을 흉내내려면 **다른 PC에서 SSMS로 접속**하거나, 접속 문자열의
`Workstation ID` 를 다르게 준 세션에서 DDL을 실행한다.

- 다른 PC에서 프로시저를 하나 만든 뒤 내 SSMS에서 **새로고침** → **내 목록에 뜨지 않는다** — 마지막 확인: 기록 없음
- **다른 사람 변경도 보기** 를 켜면 → 그 객체가 뜬다 — 마지막 확인: 기록 없음

## 2-6. Pull·Push 안내 문구

libgit2 영문 원문이 보이면 결함이다.

### Pull 성공 경로

- **원격에 새 커밋이 있는 상태.** 다른 클론에서 커밋을 만들어 원격에 올린 뒤 Pull → 안내에 **매핑된 저장소 폴더 경로**와 `[스키마]/[객체 유형]/[이름].sql` 위치 문구가 함께 뜬다. 그 폴더를 열어 안내가 가리킨 자리에 실제로 `.sql` 파일이 있다 — 마지막 확인: 기록 없음
- **원격에 새 커밋이 없는 상태.** 곧바로 다시 Pull → `원격에 새 변경이 없습니다. 저장소가 이미 최신입니다.` 가 뜨고, 목록·이력 화면이 다시 그려지지 않는다(값이 바뀐 것처럼 깜빡이면 결함이다) — 마지막 확인: 기록 없음

### Pull 실패 경로

- **HTTPS 원격.** 임시로 `git remote set-url origin https://...` 로 바꾸고 Pull → `HTTPS 원격은 DBVC가 인증할 수 없습니다. SSH 원격으로 바꾸세요.` 와 변환 예시가 뜬다. 확인 후 SSH URL로 되돌린다 — 마지막 확인: 기록 없음
- **추적 브랜치 없음.** `git checkout -b tmp` 로 새 브랜치를 만들고 Pull → `추적 중인 원격 브랜치가 없어 Pull할 수 없습니다` 와 `git push -u origin tmp` 안내가 뜬다 — 마지막 확인: 기록 없음
- **미커밋 변경이 있는 상태.** 새로고침만 하고 커밋하지 않은 채 Pull → 확인 대화상자에 **"거부됩니다. 이 경우 저장소는 그대로입니다"** 와 **"사라질 수 있습니다"** 가 **둘 다** 보인다. 창이 SSMS 뒤로 숨지 않는다 — 마지막 확인: 기록 없음
- **겹치는 미커밋 변경.** 원격이 바꾼 파일을 로컬에서 커밋하지 않고 수정한 뒤 Pull → 확인 → 안내가 뜨고 **로컬 수정 내용이 그대로 남아 있다.** (사라지면 심각한 결함이다) — 마지막 확인: 기록 없음
- **SSH 포트 문구.** 안내 목록의 포트 항목이 `원격 호스트의 SSH 포트(기본 22)가 열려 있는지` 로 표시된다. 비표준 포트를 쓰는 GitLab에서 특히 확인한다 — 마지막 확인: 기록 없음
- **OpenSSH가 없는 상태** (선택). 관리자 권한 PowerShell에서 클라이언트를 떼고 Pull → `OpenSSH 클라이언트를 설치한 뒤 다시 시도하세요` 안내가 뜬다. 확인 후 다시 붙인다 — 마지막 확인: 기록 없음
  ```powershell
  Remove-WindowsCapability -Online -Name OpenSSH.Client~~~~0.0.1.0   # 끄기
  Add-WindowsCapability    -Online -Name OpenSSH.Client~~~~0.0.1.0   # 되돌리기
  ```
  > 재현이 안 되면 `PATH`에 다른 `ssh.exe`가 남아 있는 것이다 — Git for Windows도 `ssh.exe`를 함께
  > 깐다. `Get-Command ssh -All` 로 확인한다. `core.sshCommand` 가 설정돼 있어도 DBVC는 SSH가
  > 가능하다고 판단하므로 이 안내가 뜨지 않는다 (`git config --get core.sshCommand` 로 확인).
  >
  > 안내 문구가 가리키는 경로가 **설정 > 시스템 > 선택적 기능**(Windows 11 경로)인지도 함께 본다.

### Push 실패 경로

- **원격이 앞서 있는 상태.** 다른 클라이언트(또는 웹 편집)에서 같은 브랜치에 커밋을 하나 올린다. 로컬에서 fetch/Pull하지 않은 채 스키마를 바꾸고 Commit한 뒤 Push → `원격이 '...' 갱신을 거부했습니다` 와 **"Pull을 먼저 하세요"** 문구가 뜬다. 확인 후 `git log`로 **로컬 커밋이 그대로 남아 있다** (Push는 거부돼도 저장소를 바꾸지 않는다) — 마지막 확인: 기록 없음
- **올릴 것이 없는 상태.** 커밋 없이(또는 Push를 한 번 더 눌러) Push → 오류 대화상자가 아니라 `올릴 커밋이 없습니다. 원격이 이미 최신입니다.` **정보 안내**가 뜬다 — 마지막 확인: 기록 없음
- **추적 브랜치 없음.** `git checkout -b tmp` 로 새 브랜치를 만들고 Push → `추적 중인 원격 브랜치가 없어 Push할 수 없습니다` 와 `git push -u origin tmp` 안내가 뜬다 — 마지막 확인: 기록 없음
- **SSH 원격으로의 실제 Push 성공.** 스키마를 하나 바꾸고 Commit한 뒤 Push → `커밋을 원격 저장소에 올렸습니다.` 알림이 뜨고, GitHub/GitLab에서 커밋이 실제로 보인다. **이 확인이 이 묶음에서 가장 중요하다** — `OnPushStatusError` 배선을 지나는 유일한 검증이다. 단위 테스트는 로컬/파일 전송 경로(`NonFastForwardException`)만 덮는다 — 마지막 확인: 기록 없음

- 이미 커밋 메시지를 적어 둔 상태에서 **AI 생성** → 덮어쓰기 확인 대화상자가 뜨고, **취소**하면 적어 둔 문장이 그대로 남아 있다 — 마지막 확인: 기록 없음
- 프로바이더 주소를 일부러 존재하지 않는 값으로 바꾸고 **AI 생성** → 실패해도 **DBVC 창이 그대로 쓸 수 있고, 적어 두었던 커밋 메시지가 지워지지 않는다** — 마지막 확인: 기록 없음
