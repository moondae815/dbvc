# 배포 문서 넷의 경계 다시 긋기 — 설계

> **성격: 문서 재구성. 코드 변경 없음.**
> `docs/` 아래 네 문서가 같은 내용을 나눠 갖고 있고, 그중 둘은 **같은 항목의 상태가 두 군데로
> 갈려 있다.** 문서 수는 그대로 두고 각 문서가 한 독자·한 성격만 갖도록 내용을 옮긴다.

## 1. 무엇이 잘못되었나

### 1.1 `setup-checklist.md`가 네 독자를 섞고 있다

문서 머리에 **"이 문서는 설치하는 사람의 것이다"** 라고 적혀 있다. 실제 내용은 그렇지 않다.

| 자리 | 분량 | 진짜 독자 |
| --- | --- | --- |
| 0~6단계, 8단계, `master` 기준선, AI 설정 | 약 620줄 | 설치자 (한 번 밟는다) |
| 7단계 — 버전별·기능별 검증 | 약 480줄 | 릴리스 담당자 (릴리스마다 밟는다) |
| 조직이 정해야 할 운영 규칙 | 약 70줄 | 팀 리드·DBA (읽고 정한다) |
| 알려진 제약, 막혔을 때 | 약 110줄 | 문제를 겪는 사람 |

1230줄 중 설치 절차는 절반이 안 된다. 선언과 내용이 다르면 **다음 사람이 어디에 무엇을 더할지
알 수 없다** — 실제로 0.3.0부터 0.9.0까지 모든 릴리스의 검증 항목이 여기에 쌓였다.

### 1.2 운영 규칙이 두 문서에 복제되어 있다

`rollout-announcement.md` 2절과 `setup-checklist.md`의 "조직이 정해야 할 운영 규칙"에 **거의 같은
문장이 나란히 있다.** 브랜치 자유 규칙, 딸려 오는 남의 변경, `hotfix/*` 정책과 잔여 위험, 병합
주의 3항목 — 넷 다 양쪽에 있고 서로를 가리킨다.

**이 복제는 이미 한 번 사고를 냈다.** 2026-09-09
([브랜치 정책 정정 설계](2026-09-09-dbvc-branch-policy-correction-design.md))에 `develop` 고정
규칙을 철회할 때, 같은 규칙이 네 문서에 흩어져 있어 문서별 변경표를 따로 만들어야 했다. 그 설계의
검증 항목 첫 줄이 *"네 문서가 같은 규칙을 말하는가"* 였다는 것이 문제의 성격을 말해 준다.

### 1.3 검증 항목의 상태가 두 군데로 갈려 있다

`ssms-manual-verification.md`는 `setup-checklist.md` 7단계를 **가리키면서 일부는 복사해 왔다.**

- C-1은 *"항목이 많아 여기에 옮기지 않는다 — 원문에서 체크한다"* 며 `setup` 쪽을 가리킨다.
  그런데 `setup` 7단계의 체크박스는 **전부 비어 있다.** 아무도 거기서 채우지 않는다.
- 반대로 B-1·B-2·G는 `setup`에서 항목을 가져와 날짜와 함께 체크했다. 같은 항목이 `setup`에도
  체크되지 않은 채 남아 있다.

**어느 쪽이 진실인지 파일만 봐서는 알 수 없다.** 검증 문서가 "기록이 없다는 것이지 안 했다는 뜻은
아니다"라고 적어 둔 이유가 이것이다.

### 1.4 그 밖의 중복

| 내용 | 겹치는 자리 | 판정 |
| --- | --- | --- |
| 릴리스 담당자의 빌드·산출물 확인 | `rollout` "릴리스 담당자 절차" ↔ `setup` 1단계 | 같은 명령이 양쪽에. **중복** |
| `.vsix` 설치 순서 | `rollout` 1절 ↔ `setup` 4단계 | 덮어 설치 vs 첫 설치로 **실제로 다르다.** 중복이 아니라 구분이 안 보이는 것이 문제 |
| 닫힌 백로그 항목의 사연 | `backlog` 본문의 절반 이상 (2·3·4·5·10·11번) | 남은 일을 보러 온 사람이 끝난 일을 먼저 읽는다 |

## 2. 결정

### 2.1 문서는 넷 그대로 두고 경계만 다시 긋는다

합치는 안(검증을 백로그에 흡수해 셋으로)과 쪼개는 안(운영 규칙을 독립 문서로 빼 다섯으로)을
검토하고 배제했다.

- **셋으로 합치면** `setup-checklist.md`가 지금 겪는 문제 — 한 문서 안에 두 독자 — 를 새 문서가
  그대로 물려받는다. "남은 일"과 "확인할 일"은 성격이 다르다.
- **다섯으로 쪼개면** "어디를 봐야 하나"가 다시 생기고, `rollout-announcement.md`를 폐기하게 되어
  spec 여러 곳의 링크가 깨진다.

네 독자가 실재하고 수명이 서로 다르므로 넷이 맞다.

| 문서 | 독자 | 수명 |
| --- | --- | --- |
| `setup-checklist.md` | 설치자 | 한 사람이 한 번 |
| `rollout-announcement.md` | 23명 + 조직 | 계속 참조 |
| `ssms-manual-verification.md` | 릴리스 담당자 | 릴리스마다 |
| `team-rollout-backlog.md` | 유지보수자 | 계속 참조 |

### 2.2 파일 이름은 바꾸지 않는다

`rollout-announcement.md`가 공지가 아니라 규칙의 유일한 자리가 되므로 이름이 좁아진다. 그럼에도
바꾸지 않는 이유는 **`specs/`와 `plans/`가 그 이름을 가리키기 때문이다.** 그 문서들은 그 시점의
기록이라 고치지 않는 것이 이 저장소의 방식이고, 이름을 바꾸면 고치거나 끊긴 링크를 남겨야 한다.
이름과 내용의 간극은 **각 문서 머리말 한 줄로** 닫는다.

### 2.3 한 줄 규칙 — 내용은 한 문서에만 산다

| 종류 | 유일한 자리 |
| --- | --- |
| 규칙 (조직이 정하거나 지켜야 할 것) | `rollout-announcement.md` |
| 절차 (제로에서 돌아가기까지 밟는 것) | `setup-checklist.md` |
| 확인 항목 (SSMS에서 눌러 보는 것) | `ssms-manual-verification.md` |
| 남은 일과 우선순위 | `team-rollout-backlog.md` |

네 문서 머리말에 **"여기 없는 것은 어디에"** 를 한 줄씩 넣는다. 이번 정리가 한 번으로 끝나게 하는
장치가 이것 하나다 — 규칙표가 문서 안에 없으면 다음 사람이 같은 자리에 다시 쌓는다.

### 2.4 검증 항목은 1부 → 2부 단방향으로 흐른다

1.3의 문제를 구조로 닫는다. **항목은 정확히 한 곳에만 있다.**

- **1부 "지금 남은 것"** — 아직 한 번도 확인하지 않은 항목. 밟으면 날짜를 적고 **2부로 옮긴다.**
- **2부 "회귀 스위트"** — 밟아 본 적이 있고 릴리스마다 다시 보는 항목. 끝에 마지막 확인 날짜.

같은 항목이 두 부에 동시에 있는 상태가 **정의상 존재하지 않는다.** 지금처럼 "1부에 체크, 2부에
빈칸"이 생길 수 없다.

1부의 각 묶음 머리에 **옮겨 갈 2부 묶음 번호**를 적어 둔다. 옮기는 사람이 매번 어디로 갈지
판단하지 않게 한다.

> - [ ] **`rollout-announcement.md`의 운영 규칙을 팀이 읽었고, 답이 적혔는지 확인한다.**
>       채워 넣을 칸 셋(GitLab 배포 프로젝트·릴리스 담당자·공지 채널)과 조직이 정해야 할 것들

>       갈린다.

설치자가 규칙을 **읽을** 자리는 남기되, 규칙 자체는 옮긴다.

#### 3.1.1 `7단계 — 설치 확인`에 남는 5항목

"내 설치가 돌아가는가"만 본다. 렌더링·스크롤·테마는 설치 성공 여부와 무관하므로 2부로 보낸다.

1. 저장 프로시저를 하나 `ALTER` 한 뒤 **새로고침** → 목록에 `수정`으로 뜨는지
2. 항목 선택 → **비교** 탭에 좌(이전)/우(현재) 코드가 보이는지
3. 항목 선택 → **이력** 탭에 그 객체의 커밋이 뜨는지
4. 도구 창 오른쪽 위 **버전**이 방금 설치한 `.vsix`와 같은지
5. 객체를 `DROP` 한 뒤 **새로고침** → `삭제`로 뜨고, 커밋하면 저장소에서도 파일이 사라지는지

나머지(테이블 디자이너 `추가` 판정, 비교 창 세로·가로 스크롤, 탭 오가며 배경색, 좁게 도킹,
진행 표시, 어두운 테마, 기본값 제약과 인덱스, 개체 탐색기 우클릭 이력 보기)는 2부로 간다.

#### 3.1.2 AI 절에서 빠지는 검증성 항목

설정 절차(주소·모델·키·연결 테스트·저장 확인)는 남고, **눌러 보는 것**만 나간다.

- 처음 **AI 생성** → 전송 목적지 확인 대화상자가 뜨는지
- 같은 주소로 한 번 더 → 다시 뜨지 않는지
- 스킴만(`https` → `http`) 바꾸고 다시 → **다시 뜨는지**
- 커밋 메시지가 이미 있을 때 → 덮어쓰기 확인, 취소하면 문장이 남는지
- 주소를 틀리게 하고 → 실패해도 창이 쓸 수 있고 메시지가 지워지지 않는지

`%APPDATA%\DBVC\ai-settings.json`에 키 원문이 없는지 확인하는 항목은 **설정 절차에 남긴다** —
설정을 마친 그 자리에서 보는 것이고, 검증 문서 3부가 이미 "2026-09-16 키 암호화 확인에
포함된다"로 뺀 항목이다.

#### 3.2.1 2절에 합치는 규칙

지금 2절에 있는 것과 `setup`에서 오는 것을 하나의 흐름으로 다시 쓴다. 순서는 사람이 마주치는
순서다.

1. **브랜치는 자유다. 고정 브랜치 칸은 비운다** (지금 2절)
2. **왜 남의 변경이 딸려 오는가** — 통짜 스냅샷, 기본 필터, 커밋 전 경고 (지금 2절)
3. **`develop` 병합은 무해하고 `master` 병합은 위험하다** — `feature/*`·`hotfix/*` 둘 다 (지금 2절)
4. **DB 변경은 짧게 산다** (`setup`에서)
5. **같은 객체에 대한 동시 작업은 조율한다** (`setup`에서)
6. **`hotfix/*`도 같은 정책이고, 잔여 위험은 이것이다** (`setup`에서 — 대안이 더 나쁜 이유와
   현재의 관문이 DBA의 배포 스크립트 검토라는 것)
7. **`master`에서 커밋하면 도구가 묻는다 (0.9.5)** (`setup`에서)
8. **병합은 배포·감사 클론에서 한다** — 주의 3항목 (지금 양쪽에)
9. **브랜치 이름과 커밋 메시지는 지라 티켓 키로 시작한다** (지금 2절)

6번의 잔여 위험을 적을 때 `team-rollout-backlog.md`의 "11. 미승격 변경 경고"를 가리키던 문장은
**고쳐 쓴다** — 그 항목은 0.8.0으로 닫혔고, 지금의 관문은 운영 병합 미리보기의 "확인 필요"와
DBA의 배포 스크립트 검토 둘이다.

#### 3.2.2 3절 "조직이 정해야 할 것"

`setup`의 같은 이름 절에서 오되 **아직 답이 없는 것만** 싣는다. 답이 나온 것은 2절의 규칙이
되었거나 결론 한 줄로 줄어든다.

| 항목 | 상태 |
| --- | --- |
| 드리프트 검사(`[차이 검사]`) 주기와 책임자 | **미정** — 답을 적는 칸 |
| `develop`을 리셋·force-push하는가 | **미정** — 한다면 주기와 절차를 적는 칸 |
| 같은 객체를 둘이 만질 때 어떻게 조율하는가 | **미정** — 2절 5번이 문제를 설명하고 여기가 답을 담는다 |
| 공용 계정의 권한 범위 | **미정** |
| `VIEW DEFINITION`을 어디까지 부여하는가 | **미정** — 설치 스크립트가 부여하지 않는 이유와 함께 |
| 한 사람이 한 PC를 쓰는가 | **확인됨(2026-09-10).** 결론과 "깨지면 어떻게 되는가"만 두 줄로 |

#### 3부. 뺀 항목과 이유

지금 표를 그대로 두고 **줄을 보탠다.**

  `setup`에서도 지우고, 그 사실을 이 줄에 적는다. 정보는 `setup`의 "알려진 제약"
  (전환 이전 커밋의 diff는 바이너리로 남는다)에 남는다.

## 4. 건드리지 않는 것

- **`specs/`와 `plans/`.** 그 시점의 기록이다. 파일 이름을 유지하므로 링크도 끊기지 않는다.
- **`README.md`.** 기능 설명이고 이번 경계와 겹치지 않는다. 다만 6절의 검증에서 어긋난 문장이
  생기지 않았는지 본다.
- **`user-guide.html`, `why-db-version-control.html`.** 쓰는 사람용 한 장과 설득 자료로 성격이
  이미 분리되어 있다. `why-db-version-control.html`은 게시본이 따로 있어 함께 고쳐야 하므로,
  이번에 규칙 문장을 옮기더라도 **그 파일의 규칙 문장은 바꾸지 않는다** — 옮기는 것은 `setup`과
  `rollout` 사이뿐이다.
- **릴리스 노트 템플릿의 규칙 요약.** 한 줄 규칙의 예외다. 복사해 붙여 GitLab에 올리는 것이라
  링크로 대체하면 독자가 폐쇄망에서 원문에 닿지 못한다.

## 5. 순서

문서 사이를 오가는 작업이라 순서가 있다. **내용을 옮긴 뒤에 원본을 지운다** — 반대로 하면 중간
상태에서 내용을 잃는다.

1. **검증 문서를 다시 쓴다** (3.3). `setup` 7단계와 8단계 병합 항목, AI 검증 항목을 읽어 1부·2부에
   배정한다. 이 단계에서 `setup`은 아직 그대로다
2. **`rollout`을 다시 쓴다** (3.2). `setup`의 운영 규칙을 흡수한다
3. **`setup`을 줄인다** (3.1). 1·2에서 옮겨 간 자리를 지우고, 7단계를 설치 확인으로 바꾸고,
   0단계에 체크박스를 더한다
4. **`backlog`을 다시 쓴다** (3.4)
5. **`CLAUDE.md`에 한 줄** (3.5)
6. **6절의 검증**

각 단계를 따로 커밋한다. 한 커밋에 넣으면 무엇이 어디로 갔는지 diff에서 읽을 수 없다.

## 6. 검증

자동 테스트는 없다. 상호 참조의 일관성만 본다.

- [ ] **규칙이 한 곳에만 있는가.** 특징적인 문구로 `grep` 한다 —
      `딸려`, `짧게 산다`, `hotfix`, `MR로만 병합`, `고정 브랜치 칸`. 각각 `rollout`에서만 나와야
      한다(`specs/`와 `user-guide.html`, `why-db-version-control.html`은 제외)
- [ ] **검증 항목이 한 곳에만 있는가.** `setup-checklist.md`에 `- [ ]` 로 시작하는 검증성 항목이
      3.1.1의 다섯 개와 설치 절차의 체크박스뿐인가
- [ ] **1부와 2부에 같은 항목이 없는가**
- [ ] **끊긴 링크·앵커가 없는가.** 특히 `setup-checklist.md#조직이-정해야-할-운영-규칙` — 그 절이
      사라지므로 이 앵커를 가리키는 곳을 모두 고친다
- [ ] **네 머리말의 "여기 없는 것은 어디에"가 서로 맞는가**
- [ ] **`README.md`와 어긋나는 문장이 생기지 않았는가**
- [ ] **`CLAUDE.md`의 두 참조가 여전히 맞는가** — `setup-checklist.md`(절차)와
      `team-rollout-backlog.md`(우선순위) 둘 다 성격이 유지된다

## 7. 이 정리가 성공했는지 아는 법

**다음 기능을 만들 때 문서를 어디에 더할지 묻지 않게 되는 것.** 지금은 물어야 한다 — 절차인지
규칙인지 확인 항목인지가 문서 이름으로 갈리지 않기 때문이다. 2.3의 표와 3.5의 한 줄이 그것을
닫는다.
