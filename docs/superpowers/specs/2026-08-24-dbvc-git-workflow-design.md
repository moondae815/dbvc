# DBVC 형상 관리 워크플로 설계 — 3환경·공용 개발 DB·환경 브랜치

## 1. 문제

DBVC의 Git 기능은 **단일 브랜치에서 혼자 작업하는 흐름**만 완결되어 있다. `IGitManager`가
노출하는 연산은 저장소 판별·상태 조회·커밋·Pull·Push·이력 조회·HEAD 파일 내용이 전부다.
브랜치는 오류 메시지 문자열로만 등장하고(`GitManager.cs:401`), 현재 브랜치를 화면에 띄우지도
않는다.

실제로 도입하려는 환경은 그 전제와 다르다.

### 1.1 도입 환경

- **DB 3층**: 공용 개발 DB(개발자 쓰기), 테스트 DB(개발자 쓰기), 운영 DB(DBA만 쓰기)
- **운영 DB에는 DDL 트리거를 설치할 수 없다**
- **웹 프로젝트에서 이미 쓰는 브랜치 플로우가 있다**: `master`(운영), `develop`(테스트),
  `feature/*`·`hotfix/*`는 **모두 `master`에서 분기**한다. 테스트 배포는 `develop`에 병합,
  운영 배포는 `master`에 병합
- **DB 형상 관리는 아직 도입 전이다.** 기존 저장소도 기존 규칙도 없다
- 사용자는 Git을 쓰는 개발자와 Git을 모르는 DBA가 섞여 있다. 외부 Git 클라이언트가 깔려
  있을 수도, 없을 수도 있다

`master` 기준 분기는 표준 git-flow가 아니라 **환경 브랜치 패턴**이다. 목적은 선택적 승격이다 —
feature가 서로 독립적이라 A만 `master`에 올리고 B는 남겨 둘 수 있다. `develop`은 "테스트
서버에 무엇이 올라가 있나"를 담는 통합용 브랜치일 뿐이고 아무것도 그로부터 분기하지 않는다.

이 패턴이 DB 형상 관리에 미치는 영향이 이 설계의 핵심이다: **공용 개발 DB는 어떤 브랜치의
기준선과도 일치하지 않는다.** DB는 항상 `master + 진행 중인 모든 feature` 상태다.

### 1.2 배포 스크립트를 배포에 쓸 수 없다

`BuildScriptingOptions()`가 `ScriptDrops = false`, `IncludeIfNotExists = false`로
스크립팅하고(`SmoManager.cs:140-141`), `ScriptGenerator`는 그 조각들을 `GO`로 이어 붙인다.
결과물은 **순수 `CREATE` 문의 나열**이다.

대상 DB에 이미 있는 객체에 이 스크립트를 실행하면 첫 객체에서 "이미 있습니다"로 실패한다.
테이블은 더하다 — `CREATE TABLE`은 **데이터가 든 기존 테이블을 새 모양으로 바꾸는 방법을
아무것도 말해 주지 않는다.**

DBVC는 상태 기반(state-based) 도구다. 저장소는 "스키마가 어떤 모습이어야 하는가"를 담고,
그걸 실제 DB에 적용하려면 **대상 DB와 비교해 `ALTER`를 만들어내는 엔진**이 필요하다. DBVC에는
그 엔진이 없고, 마이그레이션 스크립트 순서 관리도 없다.

### 1.3 커밋 한 번이 남의 변경을 지운다

`MarkProcessedCommand`(`StateTracker.cs:69-75`)에 `LoginName` 조건이 없다.

```sql
UPDATE dbo.DBVC_ChangeLog
SET IsProcessed = 1
WHERE IsProcessed = 0 AND Id <= @lastLogId
  AND (ObjectName = @objectName OR (...))
  AND (ISNULL(SchemaName, N'dbo') = @schemaName)
```

pending 조회(`StateTracker.cs:45`)도 `LoginName`을 SELECT하지 않아 `ChangeRecord`에 작성자
필드 자체가 없다. 공용 개발 DB에서 A가 커밋하면 **B가 방금 만든 변경까지 `IsProcessed = 1`로
닫힌다.** B 화면에서 조용히 사라지고, B는 자기가 뭘 바꿨는지 모른 채 커밋을 빠뜨린다.

`master` 기준 분기와 합쳐지면 더 나쁘다. 필터가 없으면 A의 변경 목록에 **B·C가 만든 객체가
전부 뜬다** — 그것들은 `master`와 다르니까. A가 전체 커밋하면 남의 미완성 작업이 `feature/x`에
담기고, 그 브랜치가 승격되면 검증도 안 된 남의 작업이 운영에 나간다.

### 1.4 운영 DB에 트리거를 설치할 수 있는 화면이 뜬다

`IsInitialized = probe.InstalledVersion > 0`이고(`ViewChangesViewModel.cs:367`) 미설치면
초기화 오버레이가 화면을 덮는다. **DBA가 운영 DB에 붙었다가 그 버튼을 한 번 누르면 금지된
DDL 트리거가 설치된다.** 되돌릴 수 있지만 일어나면 안 되는 일이다.

### 1.5 시작하려면 외부 Git 클라이언트가 반드시 필요하다

`ConnectRepository`는 이미 `git init`된 폴더만 받는다(`ViewChangesViewModel.cs:757`). 클론도,
init도, remote 추가도, upstream 설정도 없다. 첫 Push는 "`git push -u origin <branch>`를 직접
실행하세요"라고 안내한다(`GitManager.cs:403-404`). Git 인증은 SSH 전용이라 HTTPS만 여는 사내
GitLab에서는 도입 자체가 막힌다.

## 2. 결정

### 2.1 브랜치는 의도를 담고, 실제 상태는 추출해서 비교한다

웹 코드는 `master`에 병합한 결과물 **그 자체가 실행 대상**이라 배포하면 저장소와 운영이
정의상 같아진다. DB는 병합해도 1바이트도 바뀌지 않는다. 그래서 축이 하나 늘어난다.

| | 코드 | DB |
|---|---|---|
| 브랜치가 담는 것 | 의도 = 실제 | **의도만** |
| 배포 | 병합 → 복사 (자동으로 일치) | 병합 → **사람이 `ALTER` 작성·적용** |
| 일치 확인 | 불필요 | **필수** — 추출해서 브랜치와 비교 |

기존 브랜치 플로우(`master`/`develop`/`feature/*`/`hotfix/*`)를 **그대로 쓴다.** 새 브랜치
이름 규약을 만들지 않는다. 팀이 이미 아는 것을 쓰고, `feature/*`에 코드 변경과 DB 변경이 함께
담기는 값어치를 얻는다.

### 2.2 이번 범위는 기록·비교·배포 보조까지다

완전 자동 배포는 차이 계산 엔진을 요구한다. 이번 범위 밖이다(5장). 이번에 만드는 것은:

1. 공용 개발 DB에서 **내 변경만** 정확히 골라 커밋한다
2. 대상 DB와 브랜치의 **차이를 보여준다**
3. 실행 가능한 **배포 스크립트를 만들어 준다** — 자동화할 수 없는 것은 명시적으로 제외한다
4. 배포 후 **일치했는지 확인한다**

이것만으로도 도입 가치의 대부분이 나온다. 승격은 여전히 사람이 하되, 무엇을 옮겨야 하는지
목록이 나온다.

### 2.3 저장소 파일을 `CREATE OR ALTER`로 저장한다

`ScriptForCreateOrAlter`는 고정된 SMO 171.30.0의 `ScriptingOptions`에 실재한다(리플렉션 확인).
**추출 시점에 SMO가 그렇게 쓰게 한다.** 생성 시점 텍스트 변환이 아니다.

- 배포 대상은 브랜치의 **파일 내용**이지 개발 DB의 현재 모습이 아니다. 개발 DB에는 아직
  병합 안 된 변경이 섞여 있다. 파일에서 만들어야 하고, 파일이 이미 실행 가능하면 변환 로직이
  필요 없다
- 텍스트 치환은 주석이나 문자열 리터럴 안의 `CREATE`를 잘못 건드린다
- **이 변경은 저장소 전 파일을 한 번에 바꾼다. 아직 도입 전이라 비용이 0이다.** 나중에
  바꾸면 수천 파일이 한 커밋에 바뀌는 이력이 영구히 남는다. 지금이 유일한 타이밍이다

### 2.4 기존 테이블 변경은 자동화하지 않는다

기존 테이블에 컬럼을 더하는 것은 **기존 행을 무엇으로 채울지의 문제**라 스키마만 보고 결정할
수 없다. 틀린 `ALTER`를 자동 생성하는 것보다 "이건 손으로 하세요"가 낫다.

## 3. 설계

### 3.1 저장소 배치

원격 저장소는 하나, 로컬 클론은 환경마다 따로 둔다.

```
원격  ──  master (운영 의도) / develop (테스트 의도) / feature/*, hotfix/* (master에서 분기)
   │
   ├─ 개발자 PC : ...\dbvc\dev   → 공용 개발 DB   write   브랜치 자유 전환
   ├─ 개발자 PC : ...\dbvc\test  → 테스트 DB      deploy  develop 고정
   └─ DBA  PC  : ...\dbvc\prod  → 운영 DB        audit   master 고정
```

한 PC에 셋 다 필요하지 않다. 개발자 PC에는 `dev`와 `test`(테스트 배포를 개발자가 하므로),
DBA PC에는 `prod`만 있으면 된다.

**폴더를 나누는 이유.** 차이를 검사하려면 *해당 브랜치 상태의 작업 트리*에 대상 DB를 전체
추출해 놓고 비교해야 한다. 개발 클론과 폴더를 공유하면 검사할 때마다 브랜치를 갈아타야 하고,
미커밋 변경이 남아 있으면 체크아웃 자체가 거부된다. 폴더를 나누면 감사·배포용 클론이 자기
브랜치에 고정된 채 평생 전환하지 않는다.

`git worktree`도 같은 효과를 내지만 채택하지 않는다. LibGit2Sharp의 worktree 지원이 얇고,
사용자에게 "폴더 세 개"가 압도적으로 설명하기 쉽다.

### 3.2 매핑 확장

`mappings.json`은 지금 `(서버, DB) → 저장소 경로`뿐이다. 두 필드를 더한다.

| 필드 | 값 | 쓰임 |
|---|---|---|
| `branch` | `develop` / `master` / 비움 | 이 저장소가 고정되어야 할 브랜치. 비우면 전환 자유 |
| `mode` | `write` / `deploy` / `audit` | 허용 동작 |

기존 매핑 파일과 하위호환을 지킨다 — 두 필드가 없으면 `branch = 비움`, `mode = write`로 읽어
지금과 동일하게 동작한다. `MappingConfigSerializer`가 이 기본값을 채운다.

### 3.3 mode별 허용 동작

| mode | 추출 | 커밋·Push | 트리거 설치 | 차이 검사 | 배포 스크립트 |
|---|---|---|---|---|---|
| `write` | O | O | O | — | O (참고용) |
| `deploy` | O (전체만) | **X** | **X** | O | O |
| `audit` | O (전체만) | **X** | **X** | O | 선택 |

**`deploy`에서 커밋을 막는 것이 핵심이다.** 테스트 DB에서 나온 추출물은 새 변경이 아니라
*배포 결과*다. 커밋하면 `develop`에 자기 자신을 되먹이는 꼴이고, 배포가 덜 된 상태였다면
**덜 된 상태를 정답으로 굳혀 버린다.** 조용히 일어나고 되돌리기 어렵다.

초기화 오버레이는 `mode != write`이면 뜨지 않는다. 대신 "이 대상은 배포/감사 전용입니다"를
띄우고 차이 검사만 제공한다(1.4의 사고를 막는다).

`mode`는 실수를 막는 장치이지 보안 장치가 아니다. `mappings.json`은 사용자가 편집할 수 있는
로컬 파일이라 의도적 우회는 막지 못한다. 실제 권한은 SQL Server 계정 권한이 담당한다.

### 3.4 브랜치 이탈은 경고가 아니라 차단이다

대상을 열 때마다 `repo.Head.FriendlyName`이 매핑의 `branch`와 같은지 확인한다. `branch`가
비어 있지 않고 다르면 **화면을 덮고 아무 동작도 허용하지 않는다.**

누군가 외부 클라이언트로 `prod` 폴더를 `develop`으로 체크아웃해 둔 상태에서 차이 검사를 돌리면
**운영과 개발의 모든 차이가 "운영이 무단 변경됐다"로 보고된다.** 경고 배너로는 부족하다 —
조용히 틀린 결과를 내는 것보다 멈추는 편이 낫다.

detached HEAD, 병합 진행 중(`repo.Info.CurrentOperation != None`)도 같은 취급이다. DBVC는
저장소의 유일한 주인이 아니므로 이 상태들을 만나는 것이 정상이고, 만나면 멈춰야 한다.

### 3.5 추출: `CREATE OR ALTER`

`BuildScriptingOptions()`(`SmoManager.cs:136`)에 `ScriptForCreateOrAlter = true`를 켠다.

| 객체 타입 | 결과 |
|---|---|
| 프로시저·뷰·함수·트리거 | `CREATE OR ALTER` — 대상에 있든 없든 그대로 실행된다 |
| 테이블 | `CREATE TABLE` — T-SQL에 `CREATE OR ALTER TABLE`은 없다 |

이 옵션이 각 타입에 실제로 뱉는 텍스트는 실제 SQL Server에 붙어야 확인된다(4.1).

### 3.6 배포 스크립트: 3분류

스크립트를 만들 때 대상 DB에 각 객체가 있는지 조회해 셋으로 나눈다.

| 상황 | 처리 |
|---|---|
| 대상에 없음 (신규) | `CREATE` 그대로 담는다 — 신규 테이블 포함, 안전 |
| 대상에 있음 · 프로시저/뷰/함수/트리거 | `CREATE OR ALTER` 그대로 담는다 |
| 대상에 있음 · **테이블** | **스크립트에서 빼고 "수동 `ALTER` 필요"로 표시** |

`ScriptGenerator`가 이미 제외 목록을 헤더에 적으므로(`ScriptGenerator`의 `AppendHeader`)
셋째 줄은 그 위에 얹힌다. 제외 사유를 구분해 적는다 — 지금의 "스크립팅 불가"와 새로 생기는
"기존 테이블, 수동 처리 필요"는 사용자가 할 일이 다르다.

**스크립트의 재료는 브랜치의 파일이다.** 대상 DB에서 다시 뜨지 않는다. "`develop`에 병합된
것만 테스트에 나간다"는 규칙을 검사로 지키는 것이 아니라 **배치로 지킨다** — 테스트 클론은
`develop`에 고정되어 있고 병합 안 된 변경은 애초에 파일로 존재하지 않는다.

여기서 규칙 하나가 따라온다: **배포 전 Pull을 강제한다.** 로컬 `develop`이 낡았으면 방금
병합된 변경이 빠진다.

### 3.7 배포는 3단계 루프

1. **차이 보기** — Pull → 대상 DB 전체 추출 → 작업 트리와 비교 → 차이 목록
2. **스크립트 생성·실행** — 3.6 규칙대로 만들고, 사용자가 SSMS 쿼리 창에서 실행
3. **다시 검사** — 차이가 0이면 배포 완료. 남으면 무엇이 안 됐는지 그대로 보인다

**3번이 코드 배포에는 없던 단계이고 이 도구의 값어치가 나오는 지점이다.** 웹은 배포하면
같아지지만 DB는 "됐다고 생각했는데 안 된" 경우가 실재한다. 의존성 때문에 스크립트가 중간에
실패해도 조용히 성공한 척하지 않는다.

전체 추출은 객체 수에 비례해 오래 걸린다. `ExtractionProgress`와 `CancellationToken`이 이미
있으므로 진행률·취소가 붙는다.

### 3.8 운영 DB의 차이는 두 가지를 뜻한다

운영에 트리거를 설치할 수 없으므로 드리프트 감지는 **정기 전체 추출 후 비교**로 한다.
변경 사실은 잡지만 누가 했는지는 모르고, 추출 주기 사이에 들어왔다 되돌아간 변경은 놓친다.

차이가 나왔을 때 "미배포"인지 "무단 변경"인지 트리거 없이는 구분할 수 없다. 둘 다
**"확인 필요"**로 보고하고 판단은 DBA에게 맡긴다. 구분되는 척하지 않는다.

테스트 DB에는 트리거를 **설치할 수 있지만 하지 않는다.** 배포할 때마다 자기가 실행한 DDL이
로그에 쌓여 노이즈가 되고, 전체 추출 비교로 이미 답이 나온다.

### 3.9 작성자 필터

`LoginName`은 `DBVC_ChangeLog`에 처음부터 있는 컬럼이다(`InstallTrigger.sql:36`). 하위호환
보정 블록이 `SchemaName`·`IsProcessed`만 다루는 것이 근거다. **트리거 재설치도
`RequiredSchemaVersion` 인상도 필요 없다.** 이미 쌓인 로그에도 값이 들어 있다.

| 위치 | 변경 |
|---|---|
| pending 조회 (`StateTracker.cs:45`) | `LoginName`을 SELECT하고 `AND LoginName = @login` 추가 |
| `ChangeRecord` | `Author` 필드 추가 |
| `MarkProcessedCommand` (`StateTracker.cs:69`) | `AND LoginName = @login` 추가 |

세 번째가 1.3의 사고를 막는 자리다. 빼면 A가 커밋할 때 여전히 B의 로그가 닫힌다.

**"나는 누구인가"는 서버에게 묻는다.** 같은 접속에서 `SELECT SUSER_SNAME()`을 실행해 얻는다.
자격증명 저장소의 사용자명에서 유도하면 안 된다 — Windows 인증은 `DOMAIN\user` 형태이고 SQL
인증은 다르며, 트리거가 기록하는 `EVENT_INSTANCE/LoginName`과 **글자 단위로 같다는 보장이
없으면 필터가 전부를 걸러내 목록이 항상 빈다.** 서버에게 물으면 두 인증 방식 모두에서
정의상 일치한다.

**기본은 "내 변경만", 토글로 "전체".** 토글이 없으면 안 되는 이유가 셋이다.

- **고아 변경** — B가 퇴사하거나 커밋하지 않으면 그 로그는 영원히 열린 채 아무 화면에도 안 뜬다
- **대리 커밋** — A가 휴가 중일 때 그 변경을 누군가 올려야 한다
- **공용 계정** — 팀이 하나의 SQL 로그인을 공유하면 필터가 아무것도 하지 않는다. 손해는 없지만
  이득도 없으므로 도입 전에 확인할 값어치가 있다

전체 보기에서는 목록에 **변경자** 컬럼을 띄운다.

이 필터는 편의 기능이 아니라 **`master` 기준 분기 배치의 전제 조건이다.** 객체 단위로 남의
진행 중 작업을 걸러내는 수단은 `LoginName`밖에 없다 — 저장소에는 "누가 이 객체를 만졌나"가
없고, 공용 DB에서 추출한 파일은 전부 똑같이 "변경됨"으로 보인다.

### 3.10 커밋 시 두 가지 경고

필터가 객체 단위로 걸러 준 뒤에도 남는 위험이 둘이다. 둘 다 **경고이고 차단이 아니다** —
대부분은 실제로 정상인 경우이고, 차단하면 도구를 쓰지 않게 된다.

**경고 A — 미승격 변경을 품고 간다.** 커밋 대상 객체 `P`에 대해:

> `P@develop != P@master` 이면
> *"`dbo.P`에는 테스트에만 올라가 있고 운영에는 없는 변경이 있습니다. 지금 커밋하는 내용에
> 그것이 포함됩니다."*

누가 했는지 따지지 않는다. 남의 것이든 내 예전 것이든 **승격되지 않은 변경을 품고 간다는
사실 자체가 알아야 할 정보다.** 순수 git 연산이고 브랜치 종류를 특별 취급하지 않는다.
`hotfix/*`를 따로 다루지 않는 이유이기도 하다 — 모든 브랜치가 `master`에서 분기하므로 상황이
동일하다.

**경고 B — 남의 미커밋 작업이 딸려 온다.** 커밋하려는 객체에 내 것이 아닌 최근 `ChangeLog`
로그가 있으면:

> *"`dbo.P`는 `DOMAIN\kim`이 3시간 전에도 변경했습니다. 지금 커밋하는 내용에 그 변경이
> 포함됩니다."*

두 경고는 다른 것을 잡는다. A는 *커밋된 미승격 변경*을, B는 *아예 커밋 안 된 남의 작업*을
잡는다. 공용 DB가 하나뿐인 이상 B는 구조적으로 막을 수 없다. 알릴 수만 있다.

### 3.11 필요한 Git 연산

| 연산 | 왜 필요한가 |
|---|---|
| `Clone` | 도구 안에서 시작할 수 있어야 한다. 지금은 외부 클라이언트가 필수다(1.5) |
| `Init` + `Remote` 추가 + upstream 설정 | 첫 저장소를 만드는 경로. 첫 Push의 외부 의존을 없앤다 |
| `Fetch` | 원격 상태를 부수효과 없이 읽는다. 지금은 Pull하거나 Push가 거부돼야 안다 |
| 브랜치 목록·현재 브랜치·체크아웃 | 개발 클론은 브랜치를 전환한다 |
| 브랜치 간 파일 내용 조회 | 3.10 경고 A와 차이 검사의 재료. `GetFileContentAtHead`를 브랜치 인자를 받도록 넓힌다 |
| HTTPS 원격 + PAT | 사내 GitLab이 HTTPS만 열면 SSH 전용으로는 도입 자체가 막힌다 |

브랜치 전환·stash·충돌 해결 UI는 이번 범위에서 **후순위다.** 개발자는 `master`에서 분기한
자기 브랜치와 `develop`을 오갈 뿐이고, 감사·배포 클론은 브랜치를 고정한 채 커밋하지 않으므로
충돌이 날 자리가 거의 없다.

### 3.12 화면 변화

- 상단에 **현재 브랜치** 표시 — 비교 기준이 브랜치 내용이므로 어느 브랜치인지 모르면 diff를
  오독한다. 지금은 어디에도 안 보인다
- 목록에 **변경자** 컬럼, **내 변경만 / 전체** 토글
- 커밋 시 **경고 A·B**
- `mode != write`이면 초기화 오버레이 대신 **배포/감사 화면** — 차이 목록, 스크립트 생성,
  일치 확인
- 브랜치 이탈·detached HEAD·병합 진행 중이면 **차단 오버레이**

## 4. 검증

### 4.1 실제 SQL Server가 필요한 것

`SmoManagerIntegrationTests` 경로다. 로컬 SQL Server 없이는 Skip된다.

- `ScriptForCreateOrAlter = true`가 프로시저·뷰·함수·트리거에 `CREATE OR ALTER`를 뱉는가
- 테이블에는 무엇을 뱉는가 (`CREATE TABLE` 그대로일 것으로 예상)
- 그렇게 만든 배포 스크립트가 **객체가 이미 있는 DB에서 그대로 실행되는가**
- 작성자 필터: 두 로그인으로 각각 DDL을 실행한 뒤, 한쪽이 커밋해도 다른 쪽 pending이 남는가

### 4.2 단위 테스트로 덮는 것

- `MappingConfigSerializer`: `branch`·`mode`가 없는 기존 파일이 `write`/전환 자유로 읽히는가
- mode별 허용 동작 판정
- 브랜치 이탈·detached HEAD·병합 진행 중 판정
- 3.6의 3분류 판정 (대상 객체 존재 여부를 주입해 순수 함수로)
- 경고 A 판정 (두 브랜치의 파일 내용을 주입해 순수 함수로)
- `ScriptGenerator` 제외 사유 구분

### 4.3 SSMS 21에서 눌러 봐야 하는 것

CI가 검증하지 않는 영역이다. 여기를 건드렸다면 직접 눌러 보기 전에는 "동작한다"고 말할 수 없다.

- `mode = deploy`/`audit`에서 초기화 오버레이가 뜨지 않는가 (1.4)
- 차단 오버레이가 실제로 모든 동작을 막는가
- 배포 3단계 루프의 화면 전환
- 전체 추출 중 SSMS가 잠기지 않는가

## 5. 범위 밖

- **차이 계산 엔진 / 완전 자동 배포.** 저장소와 대상 DB를 비교해 `ALTER`를 생성하는 것.
  이번 설계는 "차이를 보여주고 실행 가능한 스크립트를 만들어 준다"까지다. 실제로 운영해 본
  뒤 판단할 일이다
- **기존 테이블 변경의 자동 `ALTER` 생성.** 2.4의 이유로 하지 않는다
- **의존성 해석.** `feature/x`의 프로시저만 승격했는데 그것이 `feature/y`의 새 컬럼을
  참조하면 실행이 실패한다. 3.7의 3단계 루프가 실패를 드러낼 뿐 예방하지는 못한다
- **마이그레이션 방식 전환.** DDL 트리거는 "무엇이 바뀌었는지"는 알아도 "어떻게 바꿨는지"는
  모른다(`EVENTDATA`에서 객체 이름만 뽑아 SMO로 현재 모습을 다시 뜬다). 마이그레이션
  스크립트를 자동 생성할 수 없으므로 DBVC의 핵심인 자동 감지가 무의미해진다
- **Object Explorer 아이콘 오버레이(Feature 10).** 공개 확장점이 없어 보류된 상태 그대로다
- **hotfix 전용 절차.** 3.10 경고 A가 모든 브랜치를 같게 다룬다. 남는 위험은 6장의 운영
  규칙으로 넘긴다

## 6. 조직이 정해야 할 운영 규칙

도구가 정할 일이 아니라 문서화할 일이다. `docs/setup-checklist.md`에 싣는다.

**DB 변경은 짧게 산다.** `feature/*`에서 DB를 고쳤으면 빨리 `develop`에 병합한다. 브랜치를
오래 들고 있을수록 공용 DB에서 같은 객체를 남이 만질 확률이 올라가고 경고 B가 매번 뜬다.
코드는 브랜치를 몇 주 들고 있어도 되지만 DB 변경은 그렇지 않다 — **DB는 이미 공유되어 있다.**

**같은 객체에 대한 동시 작업은 조율한다.** 공용 DB가 하나인 이상 `P`를 둘이 만지면 나중
사람의 코드가 남는다. 도구는 알릴 뿐 막지 못한다.

**`hotfix/*`의 DB 변경.** 개발 DB는 `master + 진행 중 feature` 상태라 거기서 뜬 스크립트에는
승격되지 않은 변경이 섞일 수 있다. 경고 A가 이를 알리지만, `P` 한 파일 안에 develop 변경과
hotfix 변경이 **섞여 들어오면** 텍스트가 어느 쪽과도 달라 판정되지 않는다. 파일 단위 비교의
한계다. 셋 중 하나를 택한다:

1. hotfix DB 변경은 **운영 백업을 복원한 별도 DB**에서 만든다 — 가장 정확하고 준비가 필요하다
2. 커밋 전 `master` 기준 diff를 **사람이 확인**한다
3. **hotfix에는 DB 변경을 넣지 않는다** — 운영 DB 변경은 정규 배포 경로로만

**`develop`을 리셋하거나 force-push하는가.** 그렇게 하는 팀이 있다. 그러면 경고 A의 기준이
흔들리고 테스트 DB 배포 이력이 끊긴다. 리셋한다면 그 주기와 절차를 정해 적어야 한다.

**SQL 로그인이 사람마다 다른가.** 팀이 공용 계정을 쓰면 3.9의 필터가 아무것도 하지 않고,
`master` 기준 분기 배치는 안전하지 않다. 도입 전에 확인한다.

## 7. 구현 순서

이 설계는 구현 계획 하나에 담기지 않는다. 셋으로 나눈다. 각각 별도의 plan 문서를 갖는다.

### 7.1 1차 — 공용 개발 DB에서 안전하게 커밋한다

**저장소를 만들기 전에 끝나야 한다.**

- 3.5 `ScriptForCreateOrAlter` — 2.3의 이유로 **반드시 여기 들어간다.** 저장소가 생긴 뒤로
  미루면 수천 파일이 한 커밋에 바뀌는 이력이 영구히 남는다
- 3.9 작성자 필터 — `master` 기준 분기 배치의 전제 조건
- 3.10 경고 B (남의 미커밋 작업)
- 3.2 매핑 확장, 3.4 브랜치 이탈 차단, 3.12의 현재 브랜치 표시

경고 A는 여기 넣지 않는다. `develop`과 `master`에 내용이 쌓이기 전에는 판정할 대상이 없다.

### 7.2 2차 — 도구 안에서 시작할 수 있게 한다

- 3.11의 `Clone`·`Init`·`Remote`·upstream 설정
- HTTPS 원격 + PAT
- `Fetch`

1차와 순서를 바꿔도 된다. 다만 **저장소를 실제로 만드는 시점보다 3.5가 앞서야 한다**는
제약만 지키면 된다.

### 7.3 3차 — 배포와 감사

- 3.3 mode별 허용 동작, `deploy`·`audit` 화면
- 3.6 3분류, 3.7 배포 3단계 루프
- 3.8 운영 드리프트 검사
- 3.10 경고 A

1차·2차가 끝나고 개발 DB에서 실제로 커밋이 쌓이기 시작한 뒤에 착수한다.
