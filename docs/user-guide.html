커밋한다

DBVC는 SSMS 21 안에서 도는 확장입니다. 데이터베이스에 가한 스키마 변경을 자동으로 잡아내 .sql 파일로 뽑고, 그것을 Git 저장소에 커밋하게 해 줍니다. 이 문서는 설치한 뒤 매일 무엇을 누르는지와 놀랐을 때 무엇을 보는지만 다룹니다.

요약

5분이면 그림이 잡힙니다

지금까지 데이터베이스는 기록되지 않았습니다. 프로시저를 누가 언제 왜 바꿨는지, 이번 배포에 정확히 무엇이 나가는지, 지금 운영에 있는 것이 승인한 그것인지 — 답할 방법이 사람의 기억밖에 없었습니다. DBVC는 애플리케이션 코드가 오래전부터 받아 온 대우를 스키마에도 주는 도구입니다.

방식은 단순합니다. 데이터베이스에 DDL 트리거를 하나 설치해 두면, 누군가 스키마를 바꿀 때마다 그 사실이 DBVC_ChangeLog 테이블에 적힙니다. DBVC 창에서 새로고침을 누르면 그 로그가 가리키는 객체만 SMO로 스크립팅해 저장소에 .sql로 떨어뜨리고, 바뀐 것을 좌우로 비교해 보여 줍니다. 마음에 들면 Commit, 그다음 Push입니다.

DBVC가 하지 않는 것

놀라는 지점은 거의 전부 여기서 나옵니다. 도구가 일부러 하지 않는 일들입니다.

하지 않는 것 그래서 실제로는 왜 그렇게 두었나
데이터베이스를 고치지 않는다 Pull로 받은 .sql은 파일로만 옵니다. 적용하려면 쿼리 창에서 직접 실행합니다 받은 스크립트를 그대로 도는 도구는 남의 미완성 변경을 내 DB에 조용히 밀어 넣습니다
배포 스크립트를 실행하지 않는다 파일을 만들어 주는 데까지가 DBVC의 몫입니다. 실행은 사람이 합니다 배포 실패의 책임과 반쯤 적용된 상태를 도구가 질 수 없습니다
브랜치를 바꾸지 않는다 전환은 외부 Git 클라이언트로 합니다. DBVC는 지금 브랜치를 보여 주기만 합니다 도구에 넣으면 미커밋 변경을 안은 채 갈아타는 사고를 도구가 거들게 됩니다
병합 충돌을 풀지 않는다 충돌이 나면 병합을 중단하고 원래대로 되돌립니다. 해결은 GitLab이나 Git 클라이언트에서 합니다 그쪽이 이미 훨씬 잘합니다
주기적으로 들여다보지 않는다 화면은 새로고침·연결·초기화·Commit 뒤에만 갱신됩니다 폴링을 붙이면 23명이 쓰는 공용 DB를 도구가 계속 두드리게 됩니다
DDL 자체를 막지 않는다 같은 객체를 둘이 만져도 막지 못합니다. 커밋 직전에 알릴 뿐입니다 공용 개발 DB가 하나뿐이라 막을 자리가 없습니다. 권한은 SQL Server 계정이 담당합니다

내 역할의 하루

역할 하루의 흐름 연결하는 저장소
개발자 2장 스키마를 바꾼다 → 새로고침 → 비교에서 확인 → 체크 → Commit → Push 개발 클론 하나 (필요하면 배포 클론도)
DBA 3장 차이 검사 → 배포 스크립트 저장... → 쿼리 창에서 실행 → 다시 차이 검사 개발·배포·감사 세 벌

개발자는 바꾼 것을 저장소에 넣고, DBA는 저장소에 있는 것을 DB에 반영하며 어긋난 것을 찾습니다. 도구는 두 방향 모두에서 파일과 데이터베이스를 비교해 보여 줄 뿐, 어느 쪽도 자동으로 바꾸지 않습니다.

1 · 공통

설치하고, 연결하고, 화면을 읽습니다

1.1 설치와 갱신

폐쇄망에는 마켓플레이스도 자동 업데이트도 없습니다. .vsix를 받는 곳은 사내 GitLab 배포 프로젝트의 Releases 하나뿐입니다. 태그가 곧 버전(v0.5.21)이고, 릴리스 노트가 공지 본문입니다.

메신저로 받은 파일, 옆자리에서 복사한 파일, 예전에 받아 둔 파일은 쓰지 않습니다. 어느 버전인지 파일만 봐서는 알 수 없고, 폐쇄망에는 그것을 대조해 볼 곳이 릴리스 목록밖에 없습니다.

1

SSMS 21을 완전히 종료합니다

떠 있으면 파일이 잠겨 설치가 실패합니다.

2

받은 파일의 차단 표시를 풉니다

다른 기계에서 옮겨 온 파일에는 Windows가 이것을 붙입니다.

Unblock-File .\DBVC.Vsix.vsix
3

파일을 더블클릭하고 UAC 창에서 "예"를 누릅니다

DBVC는 전체 사용자 설치라 관리자 권한이 필요합니다.

4

SSMS 21을 켜고 보기(View) 메뉴 > DBVC 를 엽니다

5

도구 창 오른쪽 위의 버전 숫자를 확인합니다

이 단계를 건너뛰지 않습니다. 설치 프로그램이 성공했다고 해서 SSMS가 새 것을 올렸다는 뜻이 아니고, 다시 시작하기 전에는 옛 버전이 그대로 떠 있습니다. 눈으로 확인할 자리는 여기 하나입니다.

갱신 기한

릴리스 노트에 적힌 날짜까지 올립니다. 기본은 릴리스 5영업일 이내입니다. 그 날짜가 지나면 문의는 최신 버전 기준으로만 답합니다 — 구버전에서만 나는 증상을 재현하고 추적하는 비용이 23명 규모에서 감당되지 않기 때문입니다. 0.5.18 → 0.5.19 → 0.5.20이 하루에 세 번 올라간 적이 있고, 그 사이에서 멈춘 사람은 이미 고쳐진 문제를 겪습니다.

설치가 "이미 설치되어 있다"며 거부되면 받은 파일이 지금 쓰는 것과 같은 버전입니다. 릴리스 목록에서 버전을 다시 확인하세요.

1.2 첫 연결

DBVC 창에는 서버 주소나 암호를 넣는 칸이 없습니다. 접속 정보는 SSMS 개체 탐색기의 연결에서 그대로 가져옵니다.

1

개체 탐색기에서 대상 데이터베이스를 선택하고 연결을 누릅니다

서버·데이터베이스·인증 방식·계정·암호를 그 연결에서 가져와 접속합니다. Windows 통합 인증과 SQL Server 인증을 모두 지원합니다.

암호는 디스크에 저장되지 않습니다. SSMS가 살아 있는 동안 메모리에만 있고, 닫으면 사라집니다. 다시 열었을 때는 연결을 한 번 더 누르면 됩니다.

2

저장소 연결...로 Git 저장소를 지정합니다

이미 받아 둔 폴더를 고르거나, 원격 저장소에서 새로 받습니다를 골라 SSH 주소를 넣으면 그 자리에서 클론합니다. 받을 폴더는 아직 없는 것이어야 합니다 — 실패했을 때 지워도 되는 것과 안 되는 것을 구분하기 위해서입니다.

3

용도를 고릅니다 — 이 선택이 그 저장소로 할 수 있는 일을 정합니다

개발은 변경을 추적하고 커밋합니다. 배포와 감사는 커밋하지 않고 차이만 검사하며, 고정 브랜치가 필수입니다. 자세한 것은 3장에 있습니다.

개발 클론은 고정 브랜치 칸을 비웁니다. 채우면 그 브랜치를 벗어난 동안 DBVC 창이 조회조차 되지 않아, 브랜치를 만들어 작업하는 흐름 자체가 막힙니다.

4

첫 커밋 전에 작성자 설정...으로 이름과 메일을 지정합니다

지정되지 않은 저장소에서는 커밋과 Pull이 막히고 배너가 뜹니다. 값은 그 저장소의 .git/config에만 저장되며 이 PC의 다른 저장소에는 영향이 없습니다. GitLab 계정과 같은 메일 주소를 써야 커밋이 계정에 연결됩니다 — Windows 계정에서 추정해 채워 주므로 그대로 맞는지 확인한 뒤 누르세요.

5

(개발 대상만) DBVC 초기화를 누릅니다

대상 DB에 DBVC_ChangeLog 테이블과 DDL 트리거를 설치합니다. 멱등이라 여러 번 눌러도 안전합니다. 초기화 직후에는 전체 추출이 자동으로 한 번 돌아 저장소에 기준점이 생깁니다.

이미 누군가 초기화한 DB라면 이 버튼이 보이지 않습니다 — 정상입니다.

Git 인증은 SSH만 됩니다

DBVC는 Git 자격 증명을 묻지도 저장하지도 않고, 시스템 ssh에 그대로 위임합니다. HTTPS 원격은 동작하지 않습니다 — 주소를 넣으면 네트워크를 타기 전에 거부하고 SSH로 바꾸는 방법을 안내합니다.

SSH 키 생성과 known_hosts 등록은 터미널에서 한 번 해야 합니다(ssh-keygen, ssh -T). SSMS 안에서는 호스트 키를 처음 확인하는 물음에 답할 수 없기 때문입니다. 절차는 도입 체크리스트 2단계에 있습니다.

1.3 화면 읽는 법

배너가 뜨면

배너 누를 것 그 뒤에 할 일
변경 추적기가 구버전입니다 추적기 업데이트 트리거만 다시 설치되며 DB 스키마는 바뀌지 않습니다. db_owner 권한이 필요합니다 — 없으면 사유를 알리고 기존 추적기를 그대로 둡니다
저장소가 옛 인코딩(UTF-16)입니다 전환하기 팀에서 한 사람만 누르고 나머지는 그 커밋을 Pull합니다. 전체 다시 추출이 한 번 돌아 모든 객체가 수정이 되며, 커밋은 직접 해야 합니다
커밋 작성자가 설정되어 있지 않습니다 작성자 설정... 이름과 메일을 확인하고 확인. 그때까지 커밋과 Pull이 막힙니다
저장소를 그대로 사용할 수 없습니다 화면 전체 — 고정 브랜치와 어긋났거나, detached HEAD거나, 병합이 끝나지 않았거나, (배포·감사) 커밋되지 않은 변경이 있습니다. 외부 Git 클라이언트로 정리한 뒤 다시 연결합니다

Pull·Push를 누르면 검은 콘솔 창이 잠깐 떴다 사라집니다. 위임받은 ssh.exe가 콘솔 프로그램이라 Windows가 콘솔을 새로 할당하는 것이며, 정상입니다.

무거운 작업은 SSMS의 UI 스레드 밖에서 돕니다. 진행 중에도 쿼리 편집기와 개체 탐색기는 그대로 쓸 수 있습니다. 추출에는 취소가 붙지만 Pull에는 없습니다 — 중간에 끊으면 작업 트리가 어중간한 상태로 남기 때문입니다.

DBVC 창을 열어 둔 채 개체 탐색기에서 다른 데이터베이스를 선택해도 대상이 저절로 따라가지 않습니다. 선택이 다르다는 안내가 뜨고, 연결을 눌러야 전환됩니다.

2 · 개발자

바꾼다 → 새로고침 → 커밋 → Push

공용 개발 DB 하나를 스무 명이 함께 씁니다. 그 전제가 이 장의 거의 모든 규칙을 만듭니다.

2.1 하루의 흐름

1

평소처럼 스키마를 바꿉니다

쿼리 창이든 테이블 디자이너든 상관없습니다. DDL 트리거가 발생 즉시 DBVC_ChangeLog에 기록합니다. DBVC를 켜 두지 않아도 기록됩니다.

2

새로고침을 누릅니다

로그가 가리키는 객체만 다시 스크립팅해 저장소에 씁니다. 객체가 많은 DB에서도 빠른 이유가 이것입니다. 목록에 추가·수정·삭제가 뜹니다.

3

항목을 눌러 비교 탭에서 확인합니다

왼쪽이 저장소의 이전 버전, 오른쪽이 지금 데이터베이스입니다. 좌우 줄이 정렬되고 스크롤이 함께 움직입니다.

4

담을 것만 체크하고 메시지를 적은 뒤 Commit

체크된 객체의 .sql만 커밋됩니다. 커밋된 항목은 변경 로그에서 닫혀 다음 새로고침 때 목록에서 사라집니다.

여기서 경고가 뜨면 멈춥니다 — 아래 2.2를 보세요.

5

Push로 원격에 올립니다

작업 트리와 커밋 이력은 건드리지 않으므로 실패해도 잃을 것이 없습니다. 원격이 앞서 있으면 거부되며, Pull로 받아 병합한 뒤 다시 누르면 됩니다.

2.2 "다른 작업자도 변경했습니다" — 이것이 뜨면

다음 객체는 다른 작업자도 변경했습니다. 지금 커밋하는 내용에 그 변경이 포함됩니다.

공용 개발 DB가 하나뿐이기 때문입니다. DBVC가 저장소에 쓰는 .sql은 그 객체의 통짜 스냅샷이라 일부만 떼어 낼 수 없습니다. 프로시저 P를 남이 먼저 고쳤고 내가 이어서 고쳤다면, DB의 P 안에는 둘의 작업이 함께 들어 있습니다. 내가 추출해 커밋하면 그 사람의 작업도 같이 담깁니다.

목록 자체는 걱정하지 않아도 됩니다 — 기본 필터가 켜져 있는 한 내가 만진 객체만 걸러 옵니다. 문제는 둘 다 만진 같은 객체 하나이고, 도구는 커밋 직전에 그 객체와 그 사람을 짚어 알립니다.

딸려 온 것이 어디로 가느냐가 갈립니다. feature/*는 develop에 병합되므로 develop에서 온 것이 develop으로 돌아갑니다 — 자정됩니다. hotfix/*는 master로 가므로 아직 승격되지 않은 변경이 운영에 일찍 도착할 수 있습니다. 도구는 이 경우를 아직 알리지 않습니다. 지금 관문은 DBA가 배포 스크립트를 읽는 것 하나입니다.

브랜치를 오래 들고 있지 않습니다

오래 들고 있을수록 같은 객체를 남이 만질 확률과 섞이는 양이 함께 커집니다. 코드는 브랜치를 몇 주 들고 있어도 되지만 DB 변경은 그렇지 않습니다 — DB는 이미 공유되어 있습니다. feature/*에서 DB를 고쳤으면 빨리 develop에 병합하세요.

브랜치 자체는 자유입니다. 저장소를 연결할 때 고정 브랜치 칸은 비웁니다. 전환은 외부 Git 클라이언트로 합니다. 지금 어느 브랜치인지는 도구 창 오른쪽 위, 버전 왼쪽의 브랜치: …에서 봅니다.

2.3 되돌리기와 무시 — 다른 버튼입니다

이 둘의 차이가 가장 자주 묻는 것입니다. 한쪽은 내 파일만 건드리고, 다른 쪽은 이 DB를 함께 쓰는 모두에게 적용됩니다.

되돌리기 무시
하는 일 .sql을 저장소의 마지막 커밋 내용으로 되돌립니다 되돌리기 + DBVC_ChangeLog의 행을 닫습니다
범위 내 로컬 파일만 이 DB를 함께 쓰는 모두
새로고침하면 아직 커밋하지 않은 객체는 다시 나타납니다 다시 나타나지 않습니다
데이터베이스는 둘 다 그대로입니다. DDL을 취소하지 않습니다
언제 쓰나 추출된 파일이 마음에 들지 않아 다시 뽑고 싶을 때 이 변경은 영영 git에 담지 않기로 했을 때

되돌렸는데 되살아난다

결함이 아니라 설계입니다. 되돌리기는 파일만 되돌리고 변경 로그는 건드리지 않으므로, 아직 커밋하지 않은 객체는 다음 새로고침에서 다시 추출됩니다. 목록에서 완전히 치우려면 ① 되돌린 뒤 그 항목을 커밋하거나(저장소와 이미 같으므로 커밋은 만들어지지 않고 로그만 정리됩니다), ② 무시를 씁니다.

새로 추출된 파일(상태 추가)은 되돌릴 내용이 없어 지워지며 복구되지 않습니다. 확인 대화상자가 지울 파일 이름을 먼저 보여 줍니다.

2.4 새로고침과 전체 다시 추출

새로고침은 변경 로그가 아는 것만 추출합니다. 빠른 대신, 로그가 모르는 차이는 잡지 못합니다. 전체 다시 추출은 모든 객체를 다시 스크립팅합니다 — 느리지만 저장소를 데이터베이스의 현재 상태와 맞추는 확실한 방법입니다.

전체 다시 추출이 필요한 경우는 정해져 있습니다.

  • DDL 트리거를 설치하기 전에 있었던 변경을 되찾을 때
  • XML 인덱스나 공간(spatial) 인덱스를 만들었을 때 — SQL Server가 그때만 다른 유형으로 알려 주어 트리거가 잡지 못합니다(같은 인덱스를 지울 때는 정상 감지됩니다)
  • Pull로 받은 파일이 내 데이터베이스와 어긋나 있을 때
  • 변경 로그를 지웠거나, 30일 보존 기한이 지나 행이 사라졌을 때
  • 추적기 업데이트를 눌러 0.2.6 이전 버전에서 올라왔을 때

저장소를 갓 연결해 추출물이 하나도 없을 때와 DBVC 초기화 직후에는 누르지 않아도 자동으로 전체 추출이 돌아갑니다.

일반 인덱스(CREATE/ALTER/DROP INDEX)와 sp_rename으로 바꾼 컬럼 이름은 부모 테이블의 수정으로 기록되어 정상적으로 잡힙니다. 인덱스는 테이블 .sql 안에 담기므로 따로 파일이 생기지 않습니다.

2.5 원격과 주고받기

버튼 하는 일 알아 둘 것
원격 확인 원격을 받아 받을 커밋 n개 · 올릴 커밋 n개를 위쪽에 띄웁니다 누를 때만 네트워크를 씁니다. 자동으로 갱신되지 않습니다 — 새로고침에 붙이면 응답 없는 원격이 변경 목록을 보는 일까지 느리게 만듭니다
Pull 원격의 변경을 로컬 저장소로 가져옵니다 파일만 옵니다. 데이터베이스에 적용하지 않습니다. 받은 스크립트를 확인한 뒤 쿼리 창에서 직접 실행하세요. 충돌이 나면 병합을 중단하고 되돌립니다
Push 로컬 커밋을 원격에 올립니다 실패해도 잃을 것이 없습니다. 원격이 앞서 있으면 거부되며, Pull 후 다시 누릅니다
커밋하지 않은 변경이 있는 채로 Pull을 누르면 먼저 확인을 받습니다 — 병합 중 충돌이 나면 되돌리면서 그 변경도 함께 사라질 수 있기 때문입니다(새로고침으로 다시 추출할 수 있습니다).

2.6 이력 보기

목록에서 객체를 고르고 이력 탭을 열면 그 객체의 .sql을 바꾼 커밋들이 최신순으로 나옵니다. 객체를 고르지 않으면 저장소 전체 이력이 나오고, 커밋마다 변경된 파일 목록이 함께 뜹니다. 파일을 고르면 아래에 좌우 Diff가 그려지고, 더블클릭하면 SSMS 내장 비교 창이 새 탭으로 열립니다.

개체 탐색기에서 객체를 우클릭해 DBVC: 이력 보기를 누르면 그 객체로 좁힌 이력이 바로 열립니다. 전체 이력으로가 되돌립니다. 쿼리 편집기에서 객체 이름을 선택하고 우클릭하면 DBVC: 저장소 버전과 비교로 지금 코드와 저장소를 바로 견줄 수 있습니다.

병합 커밋은 종류 열에 병합으로 표시되며 첫 부모를 기준으로 비교합니다. 객체 이름을 바꾼 커밋은 옛 이름의 삭제와 새 이름의 추가 두 줄로 나옵니다.

2.7 알아 두면 좋은 나머지

  • 테이블 .sql에 담기는 것: 컬럼 정의, 기본값(DEFAULT), 기본 키·외래 키·UNIQUE·CHECK 제약, 모든 인덱스, 확장 속성(MS_Description 등). 권한과 통계는 제외합니다 — 서버마다 달라 저장소가 환경에 종속되기 때문입니다. DML 트리거는 독립 파일로 저장됩니다.
  • 저장소 안의 경로: [스키마]/[객체 유형]/[이름].sql. Pull로 받은 파일도 여기 놓이며, 알림이 그 폴더 경로를 함께 알려 줍니다.
  • 이름을 바꾸면: sp_rename은 새 이름의 수정으로 기록되고, 옛 이름의 .sql은 커밋할 때 함께 지워집니다. SSMS 테이블 디자이너로 열 형식을 바꾸면 SQL Server가 테이블을 통째로 재작성하며 이 경로를 밟는데, DBVC는 그것을 원래 테이블의 수정 하나로 보여 줍니다.
  • 이미 저장소에 담긴 변경: 내가 먼저 커밋해 남의 코드가 이미 들어가 있으면, 그 사람의 항목을 커밋해도 담을 것이 없습니다. 이때는 커밋을 만들지 않고 목록에서만 정리하며 그 사실을 알립니다.
  • 주인 없는 변경: DBVC_ChangeLog는 30일이 지난 행을 처리 여부와 관계없이 지웁니다. 30일이 지나도록 아무도 커밋하지 않은 변경은 그 뒤 목록에 드러나므로, 누구든 커밋하거나 되돌릴 수 있습니다.
  • 다른 PC에서 만든 변경: 사람은 접속 PC(HOST_NAME())로 구분합니다. 노트북에서 만든 변경을 데스크톱에서 커밋하려면 다른 사람 변경도 보기를 켜세요.
  • 배포 스크립트·롤백 스크립트: 개발 화면에도 있지만 참고용입니다. 선택한 객체의 DDL을 단일 파일로 병합하며, 배포 쪽은 현재 DB 기준 최신 코드를, 롤백 쪽은 각 객체가 마지막으로 커밋되기 직전의 코드를 담습니다. 실제 배포는 3장의 절차로 합니다.

3 · DBA

차이를 검사하고, 스크립트를 만들고, 직접 실행합니다

운영 DB에는 DDL 트리거를 설치하지 않습니다. 그래서 DBA가 쓰는 화면은 개발자의 것과 아예 다릅니다 — 초기화도 추출도 커밋도 없고, 차이 검사와 배포 스크립트 저장... 둘뿐입니다.

3.1 클론 세 벌을 다른 폴더에 둡니다

같은 원격을 두고 로컬 클론을 용도별로 다른 폴더에 따로 둡니다. 폴더가 나뉘어 있으면 한 PC에 셋이 공존해도 서로 간섭하지 않습니다 — 클론마다 브랜치가 그대로 박혀 있기 때문입니다.

폴더 대상 용도 고정 브랜치
...\dbvc\dev 공용 개발 DB 개발 없음 — 자유롭게 전환
...\dbvc\test 테스트 DB 배포 develop 고정
...\dbvc\prod 운영 DB 감사 master 고정
어느 클론을 두느냐는 그 사람이 무엇을 하느냐로 정해집니다. 개발자는 보통 dev와 test 둘을, DBA는 셋 다 둘 수 있습니다.

3.2 용도별로 되는 것과 안 되는 것

용도 변경 추적 설치 저장소 추출 커밋 Push 차이 검사 배포 스크립트
개발 가능 가능 가능 가능 불가 가능 (참고용)
배포 불가 불가 불가 불가 가능 가능
감사 불가 불가 불가 불가 가능 가능

이것은 실수를 막는 장치이지 보안 장치가 아닙니다

배포·감사 대상에서 초기화 버튼 자체가 뜨지 않는 이유는, 운영 DB에 붙었다가 실수로 눌러 금지된 DDL 트리거를 설치하는 사고를 화면 단계에서부터 막기 위해서입니다. 실제 권한은 SQL Server 계정 권한이 담당합니다.

개발 대상에 차이 검사가 없는 것도 같은 이치입니다 — 개발 브랜치는 언제나 master + 진행 중인 모든 feature 상태라 차이 검사가 의미를 갖지 않습니다.

3.3 배포는 같은 버튼을 다시 누르는 3단계 루프입니다

1

차이 검사

원격에서 먼저 Pull한 뒤, 대상 데이터베이스 전체를 고정 브랜치와 비교합니다. 저장소에는 한 글자도 쓰지 않습니다.

2

배포 스크립트 저장...

차이 목록으로 실행 가능한 .sql 파일을 만들어 저장합니다. 제외된 항목과 그 사유는 파일 머리말에 사유별로 기록됩니다 — 반드시 읽으세요.

3

쿼리 창에서 직접 실행합니다

DBVC는 스크립트를 실행하지 않습니다. 배포 실패의 책임과 부분 적용 상태를 도구가 지지 않기 위해서입니다. 파일을 만드는 것까지가 DBVC의 몫입니다.

4

다시 차이 검사

방금 배포한 항목이 사라지면 성공이고, 남아 있으면 무엇이 반영되지 않았는지 그대로 보입니다. 새 화면이 아니라 같은 버튼을 다시 누르는 것입니다.

3.4 차이 목록의 상태를 읽는 법

상태 뜻 배포 스크립트에는
배포 필요 (신규) 브랜치에는 있는데 데이터베이스에 없습니다 타입과 무관하게 담깁니다
배포 필요 (내용 다름) 양쪽에 다 있는데 내용이 다릅니다 CREATE OR ALTER를 지원하는 타입만 담깁니다 — 아래 3.5
DB에만 있음 데이터베이스에는 있는데 브랜치에 없습니다 담기지 않습니다. 판단이 필요한 신호입니다
확인 필요 감사 전용 감사 대상의 모든 차이가 이 하나로만 표시됩니다 —

감사 대상의 차이가 "확인 필요"뿐인 이유

운영 DB에는 DDL 트리거를 설치할 수 없으므로, 차이가 나왔을 때 그것이 "아직 배포되지 않은 것"인지 "누군가 운영을 직접 손댄 것"인지 DBVC는 구분할 수 없습니다. 그래서 사유를 가리지 않고 하나로만 표시합니다. 판단은 DBA의 몫입니다.

3.5 스크립트에서 빠지는 것 — 반드시 읽습니다

배포 스크립트는 브랜치의 파일을 재료로 만들어집니다. 대상 DB에 이미 있는 객체 중 CREATE OR ALTER를 지원하는 타입(프로시저·뷰·함수·트리거)은 그대로 담기지만, 지원하지 않는 타입(테이블·시퀀스·동의어·사용자 정의 형식 등)은 스크립트에서 빠지고 사람이 직접 ALTER를 작성해야 합니다.

기존 테이블에 컬럼을 더하는 것은 기존 행을 무엇으로 채울지의 문제라, 스키마만 보고 자동으로 결정할 수 없기 때문입니다.

스크립팅에 실패해 차이를 판정하지 못한 객체도 같은 머리말에 남습니다 — 나중에 그 .sql만 열어 본 사람이 문서가 비교 전체를 덮는다고 오해하지 않도록 하기 위해서입니다.

도입 직후의 첫 배포 스크립트는 그대로 실행하지 않습니다

개발 DB의 첫 커밋은 "지금 개발 DB에 있는 것"의 사진이고, 개발 DB는 정의상 master + 진행 중인 모든 feature입니다. 그 사진에는 아직 나가면 안 되는 변경이 섞여 있습니다. 첫 스크립트는 한 줄씩 읽고 골라내세요.

3.6 master 기준선

감사 클론은 스스로 master를 채울 수 없습니다 — 추출도 커밋도 금지이기 때문입니다. master가 비어 있으면 운영의 모든 객체가 DB에만 있음으로 떠서 화면에 잡음만 남습니다.

그래서 기준선은 별도 하네스(tools/DBVC.Baseline)로 한 번 만듭니다. 운영 DB를 읽기만 하고, 트리거도 테이블도 설치하지 않으며, 커밋도 push도 하지 않습니다. 절차는 도입 체크리스트의 master 기준선을 만든다 절에 있습니다.

배포·감사 클론이 차단되면

비교의 기준은 "브랜치의 내용"인데 실제로 읽는 것은 로컬 작업 트리 파일입니다. 그 저장소에 커밋되지 않은 변경이 있으면 그 파일이 브랜치인 척하게 되므로, DBVC는 비교 전에 화면을 차단합니다.

도구 안에는 빠져나갈 방법이 없습니다. 외부 Git 클라이언트로 되돌린 뒤 (git checkout -- 등) 다시 연결하세요. DBVC는 이 클론을 더럽히지 않으므로 (추출 금지, 차이 검사는 아무것도 쓰지 않습니다) 원인은 항상 도구 밖에 있습니다.

4 · 이럴 땐 이렇게

거의 전부가 설계된 동작입니다

아래 증상은 대부분 결함이 아니라 "DBVC가 하지 않는 것"의 다른 얼굴입니다. 그래도 처음 만나면 놀라므로 여기 모았습니다.

되돌렸는데 새로고침하면 되살아납니다
설계입니다. 되돌리기는 파일만 되돌리고 변경 로그는 건드리지 않습니다. 목록에서 치우려면 되돌린 뒤 커밋하거나 무시를 쓰세요 → 2.3
Pull했는데 데이터베이스가 그대로입니다
설계입니다. 파일만 옵니다. 매핑된 저장소 폴더의 [스키마]/[객체 유형]/[이름].sql을 열어 확인한 뒤, 쿼리 창에서 직접 실행하세요.
Pull·Push를 누르면 검은 창이 깜빡입니다
정상입니다. 위임받은 ssh.exe가 콘솔 프로그램이라 Windows가 콘솔을 새로 할당합니다.
Push가 거부됩니다
원격에 먼저 올라간 커밋이 있습니다. Pull로 받아 병합한 뒤 다시 Push. 로컬 저장소는 그대로이므로 잃은 것은 없습니다.
"HTTPS 원격은 DBVC가 인증할 수 없습니다"
Git 인증은 SSH만 지원합니다. 원격 주소를 git@호스트:그룹/이름.git 형식으로 바꾸세요.
화면이 덮이고 아무것도 눌리지 않습니다
고정 브랜치와 어긋났거나, detached HEAD거나, 병합이 끝나지 않았거나, (배포·감사 클론에) 커밋되지 않은 변경이 있습니다. 배너에 사유가 적혀 있습니다. 외부 Git 클라이언트로 정리한 뒤 다시 연결하세요.
인덱스를 만들었는데 목록에 안 뜹니다
XML 인덱스나 공간 인덱스라면 생성이 감지되지 않습니다 — SQL Server가 그때만 다른 유형으로 알려 줍니다. 전체 다시 추출을 한 번 누르세요. 일반 인덱스는 부모 테이블의 수정으로 정상 감지됩니다.
내가 바꾼 것이 목록에 없습니다
사람은 접속 PC로 구분합니다. 다른 PC에서 만든 변경이라면 다른 사람 변경도 보기를 켜세요. 트리거 설치 전의 변경이라면 전체 다시 추출입니다.
커밋했는데 항목이 새로고침마다 되살아납니다
커밋은 성공했지만 변경 로그를 닫지 못한 것입니다(권한). 0.5.14부터는 그 사실과 원인을 알립니다. 추적기 업데이트를 한 번 누르세요 — 전체 다시 추출은 필요 없습니다.
커밋과 Pull이 막히고 배너가 뜹니다
커밋 작성자가 없습니다. 작성자 설정...에서 이름과 메일을 확인하세요. GitLab 계정과 같은 메일이어야 커밋이 계정에 연결됩니다.
SSMS를 다시 켰더니 대상이 비어 있습니다
정상입니다. 인증 정보는 디스크에 저장되지 않고 SSMS를 닫으면 사라집니다. 개체 탐색기에 접속한 뒤 연결을 한 번 누르세요.
Entra ID로 붙은 연결이 안 됩니다
토큰 기반이라 재사용할 수 없습니다. 사유를 표시하고 접속을 시도하지 않습니다.
GitLab MR에서 diff가 "Binary file"로 보입니다
0.5.14까지의 UTF-16 저장소입니다. 배너의 전환하기를 팀에서 한 사람만 누르고 나머지는 그 커밋을 Pull하세요. 전환 이전 커밋의 diff는 계속 바이너리로 보입니다 — 앞으로의 리뷰가 되는 것까지가 목표였습니다.
배포 스크립트에 테이블 변경이 없습니다
설계입니다. CREATE OR ALTER를 지원하지 않는 타입은 빠지고, 사람이 ALTER를 직접 씁니다. 빠진 항목과 사유는 파일 머리말에 있습니다 → 3.5
되돌리기가 실패합니다
객체 이름에 대괄호([·])가 들어 있고 이미 커밋되었거나 스테이징된 경우입니다. libgit2에 그 파일만 집어 되돌리는 방법이 없습니다.
설치가 "이미 설치되어 있다"며 거부됩니다
받은 파일이 지금 쓰는 것과 같은 버전입니다. 릴리스 목록에서 버전을 다시 확인하세요.
덮어 설치했는데 버전이 그대로입니다
SSMS를 다시 시작해야 반영됩니다. 설치 프로그램의 성공이 SSMS가 새 것을 올렸다는 뜻은 아닙니다.
새로고침이 느립니다
전체 다시 추출을 눌렀다면 정상입니다 — 모든 객체를 다시 스크립팅합니다. 진행률이 위쪽에 뜨고 취소가 붙으며, 취소해도 그때까지 추출된 파일은 남습니다. 그동안에도 쿼리 편집기는 쓸 수 있습니다.

여기에 없다면, 문의 첫 줄에 도구 창 오른쪽 위의 버전 숫자를 적어 주세요. DBVC는 누가 어떤 버전을 쓰는지 스스로 보고하지 않아, 버전을 아는 유일한 길이 이 한 줄입니다. 없으면 되묻는 왕복이 한 번 더 생깁니다.

5 · 하지 말 것

일곱 가지

  • 테스트·운영 DB에 연결한 저장소를 "개발" 용도로 만들지 않습니다 DBA 용도를 배포·감사로 골라야 초기화 버튼이 아예 뜨지 않습니다. 개발로 연결해 두면 운영 DB에 금지된 DDL 트리거를 설치하는 사고가 한 번의 오클릭으로 일어납니다.
  • DBVC_로 시작하는 이름의 객체를 만들지 않습니다 DBVC_ 접두사와 trg_DBVC_DDL_Tracker는 이 도구가 통째로 쓰는 이름공간입니다. 사용자 객체에 쓰면 변경 추적에도 추출에도 잡히지 않을 뿐 아니라, 이미 저장소에 커밋되어 있었다면 배포·감사 화면이 그것을 "배포 필요 (신규)"로 — 즉 DB에 없다고 — 잘못 보고합니다.
  • 메신저나 옆자리에서 받은 .vsix를 쓰지 않습니다 받는 곳은 사내 GitLab 배포 프로젝트의 Releases 하나뿐입니다. 파일만 봐서는 어느 버전인지 알 수 없고, 폐쇄망에는 대조해 볼 곳이 릴리스 목록밖에 없습니다.
  • 인코딩 전환하기를 각자 누르지 않습니다 여러 사람이 각자 하면 저장소 전체를 다시 쓴 커밋이 사람 수만큼 생겨 서로 충돌합니다. 한 사람만 누르고 나머지는 그 커밋을 Pull합니다.
  • 배포·감사 클론의 파일을 손으로 고치지 않습니다 DBA 커밋되지 않은 변경이 하나라도 있으면 그 파일이 브랜치인 척하게 되어 화면이 통째로 차단되고, 도구 안에는 빠져나갈 방법이 없습니다. 정상 상태라면 이 클론은 항상 깨끗합니다.
  • DB를 고친 브랜치를 오래 들고 있지 않습니다 개발 오래 들고 있을수록 같은 객체를 남이 만질 확률과 섞이는 양이 함께 커집니다. 코드는 몇 주 들고 있어도 되지만 DB는 이미 공유되어 있습니다. feature/*에서 DB를 고쳤으면 빨리 develop에 병합하세요.
  • 배포 스크립트를 읽지 않고 실행하지 않습니다 DBA 머리말에 빠진 항목과 그 사유가 적혀 있습니다. 특히 도입 직후의 첫 스크립트에는 아직 나가면 안 되는 변경이 섞여 있습니다. 지금 미승격 변경을 막는 관문은 이 읽기 하나뿐입니다.

이 방식이 성립하지 않는 환경

여러 사람이 원격 데스크톱으로 같은 서버에 붙어 SSMS를 쓰면 접속 PC 이름이 모두 같아져 작업자 구분이 되지 않습니다. 그 환경에서는 사람마다 SQL 로그인을 나눠야 합니다.
