# 팀 배포 백로그

DBVC를 팀에 공유하기 위해 남은 일. 2026-09-04 기준이며, P0 둘(UTF-8 전환, MarkProcessed 실패
알림 + GRANT)은 0.5.16으로, 커밋 작성자 신원은 0.5.17로, 작업 트리 되돌리기는 0.5.18로 끝났다
(0.5.19에서 잠긴 파일을 성공으로 세던 집계 오류를 고쳤다 — SSMS 실기 검증에서 나왔다).

## 팀 환경

이 백로그의 우선순위는 아래 환경을 전제로 매겼다. 환경이 다르면 순서가 달라진다.

- 개발자 20명, DBA 3명
- 폐쇄망 GitLab (마켓플레이스·자동 업데이트 없음)
- 공용 개발 DB 1대, 공용 테스트 DB 1대, 공용 운영 DB 1대 — **개인 DB가 없다.**
  한 DB의 `DBVC_ChangeLog`를 23명이 함께 쓴다는 뜻이고, 아래 5·6번이 여기서 나온다.

## 배포 전에 막을 것

### 1. `.vsix` 배포·갱신 채널

폐쇄망이라 자동 업데이트가 없다. 지금은 파일 복사 + 수동 설치뿐이고, 누가 어떤 버전을 쓰는지
알 방법도 없다. 0.5.15 → 0.5.16처럼 고치고 재배포할 일이 반드시 또 생기는데, 그때 23명에게
어떻게 알릴지가 정해져 있지 않다. 코드가 아니라 정책 결정이다.

## 배포 후에 채워도 되는 것

### 2. 작업 트리 되돌리기(discard) — 0.5.18로 끝남

변경 목록에서 고른 파일을 마지막 커밋 내용으로 되돌린다.
설계는 `docs/superpowers/specs/2026-09-07-dbvc-discard-changes-design.md`.

**파일까지만 되돌린다.** `DBVC_ChangeLog`의 행은 건드리지 않으므로, 아직 커밋하지 않은
객체는 다음 새로고침에서 다시 추출된다. 행을 닫는 자리는 커밋 하나로 유지했다 — 공용 DB
하나를 23명이 쓰는 환경에서 행을 닫는 것은 전역이고, 닫힌 행이 가리키던 DB의 변경은
git에 영영 담기지 않는다. 그 동작("무시")은 아래 4·5번과 한 몸으로 설계한다.

### 3. 브랜치 전환

없다. **정책으로 닫기를 권한다** — "개발 클론은 develop 고정". 도구에 넣으면 공용 DB의 상태와
체크아웃된 브랜치가 어긋나는 사고가 열린다. 공용 DB가 하나뿐이라 이 위험이 특히 크다.

### 4. ChangeLog 보존 정책

`DBVC_ChangeLog` 정리가 아예 없다. 공용 개발 DB에서 무한히 증가한다.

### 5. 미채택자 행 누적

DBVC를 쓰지 않는 사람의 DDL도 트리거가 기록하는데, 아무도 커밋하지 않으므로 `IsProcessed = 0`
으로 영원히 남아 **모두의** 새로고침 목록을 오염시킨다. 4번과 한 몸으로 설계해야 한다.

### 6. 병합 충돌 해결

도구 밖이다. GitLab이나 외부 도구로 푼다. 당분간 이대로 두는 것이 맞다.

### 7. Object Explorer 아이콘 오버레이 (Feature 10)

공개 확장점이 없어 보류. 사유는
`docs/superpowers/plans/2026-08-01-dbvc-object-explorer-overlay.md`에 있다. 그대로 둔다.

### 8. 차단된 배포·감사 클론의 막다른 길

배포·감사 클론은 작업 트리가 더러우면 `WorkingTreeDirty`로 차단되는데, 그 화면에는 변경
목록이 없어(`PanelSelector`) 2번의 되돌리기가 닿지 않는다. 도구 안에서 빠져나갈 방법이
하나도 없고 외부 git 클라이언트가 필요하다.

DBVC가 그 클론을 더럽힐 수는 없으므로(추출 금지, 차이 검사는 아무것도 쓰지 않는다) 원인은
항상 도구 밖에 있다. 그래서 자동으로 치우지 않는다 — 차단 배너 위에 사유와 함께 뜨는
별도 버튼이 필요하다. 쓰는 사람이 DBA 3명뿐이라 우선순위는 낮다.
